Pattern: editable grid

Line-item entry — a PO, an invoice, a pick list — composed entirely from existing pieces, presented as a graded path. Simple: plain text/number cells with dirty-state + Save/Cancel — that's the data-table page's multi-row inline edit, start there. Medium (first demo below): a combobox lookup cell, cell-level validation, add/remove lines. Money & unit cells: currency and unit as real separate fields inside a row. Advanced: every cell type, realtime totals, and the save-per-change mode. The full picture: a composite PO line-items editor putting all of it in one table. Zero new CSS at every step — the grid is the same primitives, composed harder.

Money & unit cells — currency/unit as real separate fields

An editable line often needs the currency or unit editable next to the number, not baked into a label. Both compose into a data-row-edit row with zero special wiring — and their precision behaviors keep working: switch this row's currency to JPY and the price reformats to 0 decimals, marks the row dirty, and Cancel restores the currency, the value, and the precision together.

Under the hood: the money/unit behaviors dispatch a real input event when they reformat, so initRowEdit()'s dirty tracking sees precision changes the same as typing; Cancel re-fires change on a reset select so the precision re-derives from the restored currency/unit instead of sticking at the abandoned one.

Advanced — every cell type + realtime totals

All the common ERP column types in one editable table: text, a native <select>, date, checkbox, and a tag-input cell — plus a footer total that recomputes in realtime (initTableSum(), declarative data-sum-of). Edit the Qty fields and watch the total; toggle, retag, then Cancel — native fields restore themselves, and the bo:row-cancel hook restores the chips.

Subtotals come in both modes: declarative auto-sum (data-sum-of="qty", shown above — a deliberate, documented exception to "you do the data") or listen to bo:cell-change (rowId/field/value on every committed edit) and do custom math — qty × price line totals, weighted sums, whatever the auto mode can't express. Tag chips are consumer-rendered, so Cancel can't restore them natively — bo:row-cancel fires after the native fields reset, exactly for that. Announce totals on COMMITTED change, not per keystroke: the visible cells update in realtime for sighted users, while a visually-hidden aria-live="polite" status (see this page's script) speaks one summary per committed edit — change fires on blur for text, immediately for select/checkbox/stepper — instead of a queue of announcements on every keystroke. The summary includes the edited line's total, giving line totals the same announcement parity as the grand total.

Save-per-change — data-row-edit="live"

The second save model: no Save/Cancel buttons, every committed change (blur for text, immediate for select/checkbox/tag) dispatches bo:row-save at once and re-baselines — wire the listener to a fetch/hx-patch and edits persist as they happen. Same markup minus the actions cell. Trade-off to know: this commits per field (a half-typed new line hits your server validation mid-row); many real ERPs commit per row-exit instead — if that's your model, keep batch mode and trigger Save from your own row-blur logic. Optimistic-update/rollback on a failed PATCH is your code's job either way; this demo only logs.

The full picture — a PO line-items editor

Everything above in one table, the generic shape of real ERP line entry: product dropdown, quantity with a unit select, price with a currency select, computed line totals, tag cost centers — dirty tracking, Cancel, and both subtotal modes all working together. Line totals are custom math (qty × price via bo:cell-change, formatted with the exported currencyDecimals()); the Qty column total is auto-sum (data-sum-of). Grand total shows "mixed" if row currencies differ — a totals decision the framework correctly leaves to you.

Two real-ERP notes before copying this shape: currency normally lives on the document (vendor/PO header), not per line — per-line selects here exist to demo the behavior; multi-currency documents need an FX rate to a document currency, and "mixed" should be a validation error in most systems. And unit prices often carry more precision than the currency's amount decimals (JPY prices quoted at 2-4 dp are normal) — put data-decimals on the price cell's option or container where your price master disagrees with ISO 4217.

What composes, and what doesn't (out of the box)

  • Combobox in a cell — no special markup; it's the same .bo-combobox as anywhere else. initCombobox() and initRowEdit() are independent document-level delegations — call both once, in any order.
  • Cell-level error — wrap the cell's input + message in .bo-form-field (a plain div; nothing form-specific about it) and it gets the exact same :has([aria-invalid]) reveal as a standalone field. margin-block-end: 0 cancels the field wrapper's normal stacking gap, which fights a dense cell.
  • data-grid-nav — deliberately NOT used above. It pulls every cell's input out of the Tab sequence (roving tabindex, one cell tabbable at a time; Enter re-enters the widget) — the right model for a mostly-read, occasionally-edited grid, but it fights rapid sequential entry, which wants every input directly tabbable. Combining them is possible (an input is still FOCUSABLE by data-grid-nav's definition, so Enter-to-focus works) but changes the interaction model app-wide — pick one per table, don't mix without a reason.
  • Add/remove line is plain app code, not a behavior — shown here as a <template> clone; a real app might fetch the row markup from the server instead (HTMX hx-get + hx-swap="beforeend"). Either way, delegation means the new row works with zero re-init.

<button class="bo-btn bo-btn--secondary" type="button" data-line-add>+ Add line</button>

<script type="module">
  import { initRowEdit, initCombobox } from "@busy-office/ui/js";
  initRowEdit(); initCombobox();     // once — delegation covers rows added later

  // Add/remove a line is plain app logic, not a framework behavior — the
  // framework has no opinion on WHERE new rows come from (a <template>
  // clone here; your app might fetch a fragment from the server instead).
  let n = 1;
  document.querySelector("[data-line-add]").addEventListener("click", () => {
    n += 1;
    const tbody = document.querySelector("[data-row-edit] tbody");
    const row = document.getElementById("line-template").content.cloneNode(true);
    const tr = row.querySelector("tr");
    tr.dataset.rowId = `LINE-${n}`;
    // Combobox listbox ids must be unique per row — reusing one id across
    // cloned rows is the exact collision bug fixed 2026-08-15 (widget #2
    // silently driving widget #1). Give each clone its own pair.
    const list = row.querySelector("ul");
    list.id = `line-${n}-list`;
    row.querySelector('[role="combobox"]').setAttribute("aria-controls", list.id);
    tbody.appendChild(row);
    tbody.lastElementChild.querySelector("input").focus();
    // No re-init call: initRowEdit()/initCombobox() are document-level
    // delegation — the new row's input and combobox work immediately.
  });
  document.addEventListener("click", (e) => {
    const btn = e.target.closest("[data-line-remove]");
    if (btn) btn.closest("tr").remove();
  });
</script>
