Versioning & upgrades

What counts as the public API — the surface a version bump can break — and why moving off the framework stays cheap.

What is (and isn't) API

  • API (breaking it = a major version): semantic tokens, documented class names, and data-*/ARIA contracts. The API tables on every component page are generated from the shipped CSS, so what's documented is exactly what's contractual.
  • JS is API too: the exported init*/refresh* function signatures and the bo:* intent-event payload shapes (the generated table on JS behaviors). Removing or reshaping an event's detail field is a Breaking change and gets a CHANGELOG Breaking entry — pre-1.0 that means a minor bump with the entry; post-1.0, a major.
  • Not API: component-internal selectors and the raw palette tier (--bo-palette-* may change in any release — style against the semantic tier). Per-component dist file placement is also not API until v1.0 — à-la-carte importers should pin versions.

Docs policy

Docs describe the latest version; pinned users read the CHANGELOG, which records every pre-1.0 breaking change (including the eof- → bo- prefix rename). Versioned docs arrive with 1.0.

Leaving is cheap — by design

The cascade contract means your unlayered CSS already outranks the framework; a migration away is incremental overrides, not a rewrite. That's deliberate: an exit story you can verify beats a lock-in you have to trust.
