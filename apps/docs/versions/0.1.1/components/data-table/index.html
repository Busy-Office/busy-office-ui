Data table

Check a row — the bulk-action toolbar appears via :has(), zero JS. Sticky header, tabular numerals, density-aware row heights, container-query auto-compaction below 480px container width. Two tiers, same markup family: Simple (below) covers selection/sort/filter for free; reach for Advanced (data-grid-nav + initDataGrid(), further down this page) only when a screen genuinely needs full two-axis keyboard navigation — most tables don't.

Toolbar — column visibility & export opt-in

Invoice # Vendor Cost center Amount Status
INV-10234 Acme Supply Co. CC-4021 $4,208.00 Pending
INV-10235 Globex Industrial CC-4021 $18,940.50 Approved
INV-10236 Initech GmbH CC-1180 $730.25 Rejected

Columns is the same multi-select dropdown pattern as elsewhere (data-multiselect, real checkboxes) — checking/unchecking a data-col-toggle box shows/hides every <th>/<td> with the matching data-col, scoped to this table only. Export dispatches bo:table-export with a format — this behavior only tracks the intent, generating and downloading the actual file is your code (fetch a server export endpoint, or build a client-side CSV/PDF) — same split as bo:row-save and bo:scan. Try it: uncheck a column, then click Export.

Advanced — keyboard grid navigation opt-in

The second tier: data-grid-nav + initDataGrid() turns the table into a WAI-ARIA APG "Grid": role="grid" (cells get their gridcell/columnheader roles implicitly — no per-cell markup needed), aria-selected synced from the row checkboxes, and two-axis roving tabindex — Tab enters the grid at ONE cell, arrow keys move the cursor (clamped, no wrap), Enter focuses a cell's single widget (the checkbox), Esc hands focus back to the cell. Reach for this when a screen is genuinely spreadsheet-like (dense data entry, heavy keyboard use) — the Simple tier above is enough for most tables, including ones with sort and bulk-select. Click into the table below, then try arrow keys.

Multi-row inline edit — dirty state + save/cancel

This is the simple starting point of the editable-table path — plain cells, dirty badge, Save/Cancel. The graded continuation (combobox lookup cells, every cell type, realtime totals, save-per-change, a full PO line-items editor) lives on the Editable grid pattern.

ItemQtyActions
Widget A Unsaved
Widget B Unsaved

Same seamless input as above, plus data-row-edit on the table: typing marks the row data-row-state="dirty" (amber tint, same visual channel the error row state uses) and reveals that row's badge + Save/Cancel. Cancel resets the row's inputs to their last-saved value; Save dispatches a bo:row-save event with the row and its data-row-id — your code persists it (fetch, hx-patch, form submit), this behavior only tracks dirty state. Try it: edit a quantity below.

Performance at scale — measured, not guessed

Measured 2026-08-15 against the full table stack (sticky header, row checkboxes, badges, container query, initDataTables()) in the examples/po-app stress harness (/stress?n=…):

RowsInitial renderSelect-allPost-bulk-check style flush
1,00085 ms4 msnegligible
5,000174 ms18 ms231 ms
20,000558 ms49 ms610 ms
5,000 4× CPU throttle1,625 ms15 ms174 ms
20,000 4× CPU throttle3,783 ms60 ms686 ms

The 4×-throttle rows approximate older corporate hardware (added after the decisions grill challenged the single-machine evidence). Render and scroll scale linearly with no cliff; the recurring cost is the bulk-select style recalculation (the selected-row tint re-evaluating per row) — it repeats on EVERY bulk toggle, staying under 700 ms even throttled. The genuine pain point is initial render at 20k rows on slow hardware (~3.8 s). Practical guidance: a few thousand rows are fine as-is; beyond that, paginate server-side (page numbers or load-more) — which dense ERP screens want anyway for findability. There are no virtualization hooks: windowing breaks Ctrl-F, select-all semantics, and screen-reader row counts, and pagination is the answer at the scale where tables stop being scannable. Re-open condition, not dogma: if a real deployment measures interaction costs breaching ~1 s at row counts it genuinely cannot paginate, the /stress harness in examples/po-app is kept for exactly that re-measurement.

No grouping component exists because none is needed — this composes from plain HTML table semantics the CSS already styles: one <tbody> per group, the group header a <th scope="rowgroup" colspan> row (bold by default; the scope declares it heads its <tbody> — screen-reader support for rowgroup association varies, so keep group names ALSO in prose/ captions when the grouping is load-bearing), subtotal and grand-total rows are ordinary rows using __col--right/__col--numeric. Proven in the examples/po-app "Spend by cost center" screen, both themes. Don't combine with --striped (stripes land arbitrarily on summary rows) or with row-select/sort (sorting across grouped bodies is your code's problem — regroup server-side instead).

Column alignment

Put the same modifier on the <th> and every <td> in a column: --left, --center, --right, or --numeric (right-aligned and tabular figures, for amounts).

JS required Optional but recommended: initDataTables() — select-all, live count, O(1) toolbar reveal, swap re-derive. Without it: selection visuals work via :has(); select-all is inert.
  • Sorting contract: the framework paints the indicator from aria-sort on the <th>; re-ordering rows and updating the attribute is YOUR code (server or client).
  • Row checkboxes need name/value to POST selections (via hx-include or a form).
  • Columns marked __col--secondary hide under container compaction — keep that data reachable (row detail view) per WCAG 1.4.10.
  • Separately opt-in: data-grid-nav + initDataGrid() for the full WAI-ARIA APG Grid pattern (two-axis keyboard navigation). Off by default — a read-only reference table does not need per-cell Tab stops.
  • Separately opt-in: data-row-edit + initRowEdit() for multi-row inline edit with per-row dirty state and Save/Cancel. Tracks state only — persistence is your code, via the bo:row-save event.
  • Separately opt-in: data-col-toggle/data-table-export + initTableToolbar() for column visibility (composes with the multi-select dropdown, no new markup) and an export intent (bo:table-export — generating the file is your code). Rows appended later (load-more, swaps) don't inherit hidden columns — call initTableToolbar() again after appending, same re-call convention as initDataTables().

Markup — the canonical table recipe

<!-- tabindex="0": the container scrolls when the table
     overflows, and a scrollable region must be keyboard-reachable -->
<div class="bo-data-table-container" tabindex="0">
  <div class="bo-data-table__toolbar">
    <div class="bo-data-table__bulk-actions" role="group" aria-label="Bulk actions">
      <button class="bo-btn bo-btn--secondary" type="button">Approve</button>
    </div>
    <span class="bo-data-table__selection-count"></span> <!-- live "n selected" -->
    <input class="bo-input" type="search" aria-label="Filter invoices" />
  </div>
  <table class="bo-data-table">
    <thead><tr>
      <th scope="col"><input type="checkbox"
          class="bo-checkbox bo-data-table__select-all" aria-label="Select all" /></th>
      <th scope="col" aria-sort="ascending">
        <button class="bo-data-table__sort-btn" type="button">Invoice #</button>
      </th>
      <th scope="col" class="bo-data-table__col--numeric">Amount</th>
    </tr></thead>
    <tbody><tr>
      <td><input type="checkbox" name="id" value="INV-1"
          class="bo-checkbox bo-data-table__row-select" aria-label="Select INV-1" /></td>
      <!-- name/value make the selection POSTable:
           hx-include=".bo-data-table__row-select:checked" or a plain form. -->
      <td class="bo-data-table__col--code">INV-1</td>
      <td class="bo-data-table__col--numeric">$4,208.00</td>
    </tr></tbody>
  </table>
</div>
<script type="module">
  import { initDataTables } from "@busy-office/ui/js";
  initDataTables(); // select-all, live count, O(1) toolbar reveal
</script>

     aria-sort on the <th>; the CSS draws the indicator from aria-sort. -->
