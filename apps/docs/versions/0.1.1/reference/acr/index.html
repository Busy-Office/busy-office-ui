Accessibility Conformance Report

A VPAT-2.5-shaped report — WCAG 2.2, Level A + AA (applicable subset for a CSS/JS UI toolkit — criteria with no toolkit surface, e.g. captions/audio, are omitted, not silently marked Supports) — generated from the same facts the build gates already produce (contrast pairs, keyboard map, event/ARIA coverage, forced-colors emulation), not typed by hand. This is not a substitute for a licensed accessibility auditor's ACR — it's the honest, machine-checkable slice: automated evidence is cited by number and regenerates every build, and a row with no automated evidence is marked Not Evaluated, never inferred as Supports.

Summary

9 Supports 5 Conditional-on-adopter 2 Not Evaluated

Automated evidence (contrast, keyboard-map, event/ARIA generation, forced-colors emulation) is cited by number and regenerates every build; rows with no automated evidence are Not Evaluated, never inferred as Supports.

Criteria generated

SC Criterion Level Conformance Remarks
1.1.1 Non-text Content A Conditional-on-adopter Icons (icon) are decorative masks — the adopter's visible label carries the meaning, per the documented aria-hidden convention. An icon-only control must supply its own aria-label; the framework cannot author that text.
1.3.1 Info and Relationships A Conditional-on-adopter Structure rides on real semantics — native <table>/<dialog>/<details>, ARIA roles/states in markup contracts across 30 components. Relationships the adopter supplies (label text, row data) are outside framework control.
1.4.1 Use of Color A Supports Two-channel doctrine: every state signal ships a visible non-color cue (glyph, border, position) alongside color. Forced-colors verification (below) is the automated proof this isn't just a style guideline.
1.4.3 Contrast (Minimum) AA Supports 64/64 token pairs pass AA across both themes plus the brand preset — computed from shipped token values on every build (check-contrast.mjs); a failing pair blocks the release.
1.4.4 Resize Text AA Conditional-on-adopter Sizing uses rem/relative units throughout; the installation skeleton explicitly forbids user-scalable=no. An adopter who hardcodes px or adds that meta tag overrides this.
1.4.11 Non-text Contrast AA Supports Non-text pairs (borders, focus rings, icon fills) are included in the same contrast.json gate as text pairs — not a separate, weaker check.
1.4.13 Content on Hover or Focus AA Not Evaluated Popover-based surfaces (combobox, dropdown, dialog) dismiss via native popover/Esc, which is dismissible/hoverable by construction — but "persistent until dismissed or invalid" per-surface has not had a dedicated manual pass.
2.1.1 Keyboard A Supports 4 behaviors ship documented, generated keyboard support (initCombobox, initDataGrid, initDialogs, initTabs); everything else is native (a plain input, a native dialog's own focus trap) or has no keyboard surface — see the generated table on JS behaviors.
2.1.2 No Keyboard Trap A Supports dialog uses a real focus trap (Tab/Shift+Tab cycle, Escape closes via native showModal()) — never an unclosable trap. data-table's grid-nav Escape returns focus from a cell's widget to the cell.
2.4.3 Focus Order A Not Evaluated DOM order matches visual order everywhere audited manually this session, but a systematic focus-order sweep across all components has not been performed. data-table's row-edit Save/Cancel move focus to the row's first field before hiding themselves (an adversarial-review find: focus previously dropped to <body> mid-table).
2.4.7 Focus Visible AA Supports A single :focus-visible ring token is used framework-wide (never suppressed) — included in the 1.4.11 non-text contrast pairs, so its visibility is contrast-gated, not just present.
3.2.1 On Focus A Supports No shipped behavior triggers navigation or a context change purely on focus — all state changes (open, filter, activate) are click/keydown-gated.
3.3.1 Error Identification A Conditional-on-adopter The form error contract (aria-invalid + aria-describedby + a message element, role="alert" if dynamic) is documented and demoed at both field and cell granularity (editable-grid pattern) — but the adopter writes the actual error text and wires aria-invalid from their own validation.
3.3.2 Labels or Instructions A Conditional-on-adopter Every form field demo shows a real <label for>; the framework enforces nothing at build time that would catch an adopter shipping an unlabeled input (no axe-in-CI gate on consumer apps, only on these docs).
4.1.2 Name, Role, Value A Supports 10 intent events and 21 behaviors keep ARIA state (aria-expanded, aria-selected, aria-current, aria-sort, …) in sync with interaction — generated event/keymap tables exist specifically so this claim has evidence instead of prose.
4.1.3 Status Messages AA Supports Live-region behaviors ship for the cases that need one without a focus change: data-table selection count and RF-scanner confirmation (initScanInput, JS-only — no CSS surface of its own), skeleton loading regions (role="status").

What "Not Evaluated" means here

Two criteria above, plus the broader assistive-technology ledger (VoiceOver, NVDA verbalization), require a human running real AT hardware — nothing this build environment can automate. They stay Not Evaluated rather than being inferred Supports from adjacent automated passes. Runtime evidence, once gathered, gets recorded and cited here — see the honest-status ledger.
