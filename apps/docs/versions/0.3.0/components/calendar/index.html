Calendar

A month grid that says which days are special — public holidays, a plant shutdown, period-end, the dates a shipment cannot land on. Use it to show a calendar, and — with each day as a real submit button — to pick from one when which days are special is part of the choice. For a plain date with no such context, use the native <input type="date">: it is localized, one tab stop, and native on a phone.

Weekends are hatched, the holiday carries a dot, today is outlined and the chosen day is filled. Every one of those is a shape as well as a colour, and each writes its meaning into the cell as visually-hidden text — so the grid reads the same in greyscale, under forced colours, and to a screen reader.

Monday-first is ISO 8601 and usual across Europe and much of Asia; Sunday-first is standard in the US, Canada, Japan and much of Latin America. An ERP shipped to a US buyer with a Monday-first delivery calendar is simply wrong for them, so both must be possible.

The framework deliberately ships no data-week-start. There is nothing for it to do: this CSS contains no positional rule — no nth-child, and “closed” is a per-cell attribute you set, not a column. Week start changes which date sits in which cell, which is decided where you generate the month. An attribute that styled nothing would be API we could never remove.

Generate the grid, do not hand-write it: a month is 35+ cells whose date must agree with its column, and an error there is invisible — the grid still looks like a calendar. Both demos above come from one function, and a build gate checks every calendar in these docs by reading each cell's datetime back against its column heading.

Each day is a real <button type="submit"> carrying its own ISO date, inside a plain <form method="get">. Click one and the date is in the URL. The server decides what is selectable — weekends and the public holiday are rendered disabled, so the rule that blocks them lives where the works calendar already lives, not in a client-side config you have to keep in sync.

No roving tabindex, no aria-* from us, no widget: real buttons in a real table already give keyboard operation, disabled semantics and a screen-reader announcement of the column and row. This works with scripting switched off.

The honest cost: it is a tab stop per selectable day — twenty in the month above, once the weekends and the holiday are out. A native <input type="date"> is one. So use the native input for a plain date, and reach for this only when seeing which days are special is part of the decision — a delivery date around a plant shutdown, a period-end close. That is a narrow case, and it is the whole case.

Why the framework does not ship a date-picker widget

The native date input is good and this framework keeps recommending it. What it cannot do is the whole reason for this component: its only constraints are min, max and step — which describe a range. A works calendar is a set: eight public holidays, a two-week shutdown, the last working day of each period. There is no attribute for that, and no API to mark a day.

So the division of labour is: the browser owns the ordinary case, this owns the case where the marks matter. Most date entry is ordinary — use the native input. When the marks are part of the decision, the section above picks from this grid with real submit buttons and no JavaScript.

What is still refused is the widget: a scripted popup with roving tabindex, its own ARIA and a month-navigation model to re-implement. That is a large surface to own badly, and nothing above needs it — which is the test for whether refusing was right.

It is a real <table> because a month is tabular data. That buys row and column semantics, scope headers and a caption for free: a screen reader announces "Tuesday, 12" without a line of ARIA. Each day carries a <time datetime>, so the machine-readable date is in the markup rather than inferred from the number.

The assembled screen lives in Patterns

Month grid + a day-detail list, swapped in beside it without re-rendering the month — the same swap discipline master-detail uses for a list and a record — is the schedule pattern. This page documents the calendar itself; the pattern documents the screen.
