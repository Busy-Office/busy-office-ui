Forms

Form fields, sections, and layout for data entry. Validation state is CSS-driven via :has(), paired with the ARIA attributes that make it announced.

Fields — label, hint, error

Registered vendor name (required — note the automatic asterisk)
Unknown cost center code
View code 
<form class="bo-form-row" novalidate>
  <div class="bo-form-field">
    <label class="bo-form-field__label" for="vendor">Vendor</label>
    <input class="bo-input" id="vendor" required aria-describedby="vendor-hint" placeholder="Acme Supply Co." />
    <span class="bo-form-field__hint" id="vendor-hint">Registered vendor name (required — note the automatic asterisk)</span>
  </div>
  <div class="bo-form-field">
    <label class="bo-form-field__label" for="amount">Amount (USD)</label>
    <input class="bo-input bo-input--numeric" id="amount" type="number" step="0.01" inputmode="decimal" value="4208.00" />
  </div>
  <div class="bo-form-field">
    <label class="bo-form-field__label" for="cc">Cost center</label>
    <input class="bo-input bo-input--code" id="cc" required aria-invalid="true" aria-describedby="cc-error" value="CC-XXXX" />
    <span class="bo-form-field__message" id="cc-error">Unknown cost center code</span>
  </div>
  <div class="bo-form-field">
    <label class="bo-form-field__label" for="status">Status</label>
    <select class="bo-select" id="status">
      <option>Pending</option>
      <option>Approved</option>
      <option>Rejected</option>
    </select>
  </div>
</form>

The error visuals are pure CSS (:has() on the field wrapper reads aria-invalid) — the ARIA half (aria-invalid + aria-describedby) is what reaches a screen reader. Both halves are the contract. This error is present at load, so it carries no role="alert": add one only when the message arrives after load. What the message says: name the violated constraint and include the datum the user needs to act — “Unknown cost center code”, or the editable grid’s “Exceeds on-hand (200)” — never a bare “Invalid value”. (Screen-level voices differ by design: the validation summary opens with “There is a problem”, and document-level strips say what is still possible — each stated on its own page.)

A .bo-form-section is a real <fieldset> (its legend is the group's accessible name), and .bo-form-actions sticks to the bottom — the framework sets scroll-padding-block-end on the scroll container so keyboard focus is never hidden underneath it. The full multi-section edit screen, with its data contract and dirty-state handling, is the detail-form pattern.

Dependent selects (HTMX)

View code 
<div class="bo-form-row">
  <div class="bo-form-field">
    <label class="bo-form-field__label" for="dep-country">Country</label>
    <select class="bo-select" id="dep-country" name="country"
        hx-get="/cities" hx-trigger="change" hx-target="#dep-city" hx-swap="innerHTML">
      <option value="">Select a country…</option>
      <option value="DE">Germany</option>
      <option value="US">United States</option>
    </select>
  </div>
  <div class="bo-form-field">
    <label class="bo-form-field__label" for="dep-city">City</label>
    <select class="bo-select" id="dep-city" name="city" disabled>
      <option value="">Select a country first</option>
    </select>
  </div>
</div>

Picking a country repopulates the city select — plain hx-get/hx-trigger="change"/ hx-target on the driving .bo-select, same attributes every other swap on this page uses. No framework surface needed: this composes entirely from existing markup.

Escalate only when this stops fitting. A hidden element with hx-trigger="change from:#driving-select" decouples the listener from the select itself when several independent things need to react to one change. OOB swaps update several dependent selects from one response when a single field drives more than one of them at once. Reach for a small htmx:afterSwap/htmx.ajax() handler only for real conditional branching a declarative trigger can't express, and sparingly — it is the one strategy here that adds JS.

Not swapping the whole form. Re-rendering the entire <form> on every change is the one shape to avoid: focus moves to wherever the swap lands, values in fields the change didn't touch can be dropped by a naive server render, and a screen reader gets no signal about what actually changed. The same reasoning already governs this framework's swap targets elsewhere — master-detail's panel is deliberately a narrow swap target, never a navigation, so the list around it never loses its place.

Label-start sections

Invoice header
From the vendor master; override per invoice.
View code 
<fieldset class="bo-form-section bo-form-section--label-start">
  <legend class="bo-form-section__legend">Invoice header</legend>
  <div class="bo-form-field">
    <label class="bo-form-field__label" for="ls-vendor">Vendor</label>
    <input class="bo-input" id="ls-vendor" value="Acme Supply Co." />
  </div>
  <div class="bo-form-field">
    <label class="bo-form-field__label" for="ls-terms">Payment terms</label>
    <select class="bo-select" id="ls-terms">
      <option>Net 30</option><option>Net 60</option>
    </select>
    <span class="bo-form-field__hint">From the vendor master; override per invoice.</span>
  </div>
  <div class="bo-form-field">
    <label class="bo-form-field__label" for="ls-note">Internal note</label>
    <textarea class="bo-input" id="ls-note" rows="3">Q3 blanket order.</textarea>
  </div>
</fieldset>

--label-start puts every field's label in a shared column instead of stacking it above — the dense two-column shape classic ERP detail screens use. The values are top (the default above, unchanged) and start, not left/right: start is logical, so it flips to the visual right under dir="rtl", and "right" was refused outright — no major design system ships a label to the right of a text field, because it puts the value in front of the reader before they know what it labels. Different label lengths ("Vendor" vs "Payment terms") still start every control at one shared edge — the section is a CSS Grid and each field a subgrid row, the exact technique key-value facts already ships for read-only rows, reused rather than invented twice. Section-level and all-or-nothing on purpose — fields inside share one label column or the section doesn't use this at all; there is no per-field override. Not combinable with .bo-form-row — the two answer the same "how do I lay out several fields" question two different ways. Below 30rem the section collapses back to labels-on-top on its own, the same width every other collapsing container in this framework (tabs, stepper, the data table) uses — resize this page narrow to see it happen with no JS and no breakpoint of your own.

Choices

View code 
<div class="bo-cluster">
  <label class="bo-choice"><input type="checkbox" class="bo-checkbox" checked /> Notify approver</label>
  <label class="bo-choice"><input type="checkbox" class="bo-checkbox" disabled /> Disabled option</label>
  <label class="bo-choice"><input type="radio" name="pri" class="bo-radio" checked /> Normal</label>
  <label class="bo-choice"><input type="radio" name="pri" class="bo-radio" /> Urgent</label>
  <label class="bo-choice">Urgent first <input type="checkbox" class="bo-checkbox" /></label>
</div>

A checkbox/radio's label sits wherever its text sits in the markup — .bo-choice is a plain inline-flex pairing with no positional CSS, so "the label on the left" or "on the right" is just which side of the input the text is written on (the last item above). This is why choice controls get no --label-start modifier: the effect the modifier gives text fields, choices already have for free.

Markup — the canonical field recipe

<div class="bo-form-field">
  <label class="bo-form-field__label" for="cc">Cost center</label>
  <input class="bo-input bo-input--code" id="cc" required
         aria-invalid="true" aria-describedby="cc-error" value="CC-XXXX" />
  <span class="bo-form-field__message" id="cc-error">
    Unknown cost center code
  </span>
</div>
