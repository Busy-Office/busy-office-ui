Pattern: kanban board

Who uses it: whoever needs to see WHERE a batch of things stands, all at once — a production planner watching orders move through stages, a fulfilment lead watching shipments. How often: a screen left open, glanced at through a shift. What "done" looks like: every card in the lane that matches its real state, and moving one is a single deliberate act. Not for finding one specific record — that is list report, grouped by status if stage is what matters; a board earns its place only when the SHAPE of stages side-by-side is the thing being read, not any one row's fields. Not drag-and-drop — moving a card here is a menu action, not a drag gesture; see why below.

Why no drag, in this baseline

A card's stage is changed through Move to… in its own action menu, never by dragging. This is the baseline verdict from the pattern's own grill (100.1): drag has no accessible substitute that has ever stabilized — the ARIA properties written for it (aria-grabbed, aria-dropeffect) were deprecated in ARIA 1.1 for being unreliably implemented, so a real drag implementation means hand-rolling a second interaction model (pick up / move / drop + live-region narration) and maintaining it forever alongside this one. The menu already gives every card a keyboard path, a screen-reader-announced result, and a touch target that works with gloves. Slice 110.7 re-grills whether drag earns its cost specifically for this screen — this page ships the accessible baseline first, and gains drag only if that grill says so.

The board

Queued 3

  • WO-4471 · Hydraulic pump assy

    Line 2 · due 28 Aug

  • WO-4472 · Seal kit batch

    Line 1 · due 29 Aug

  • WO-4473 · Filter cartridge run

    Line 3 · due 30 Aug

In progress 1

  • WO-4468 · Gearbox housing

    Line 2 · started 08:12

Blocked 1

  • WO-4460 · Valve manifold

    Parts short since 09:40

Done 2

  • WO-4455 · Bracket set

    completed today 07:50

  • WO-4451 · Pump seal

    completed yesterday

Every lane's count is a badge in its header — the monitoring signal, readable without opening a single card. A card ageing in one lane (Blocked, "since 09:40") is visible the same way an inbox row's age is: text, not colour alone.

Markup

<!-- One lane. Widget + a plain list of cards; each card's move
     action is a dropdown menu, not a drag handle. -->
<section class="bo-widget">
  <div class="bo-widget__header">
    <span class="bo-widget__title">Queued</span>
    <span class="bo-badge">3</span>          <!-- the monitoring signal -->
  </div>
  <div class="bo-widget__body">
    <ul class="bo-stack bo-stack--tight docs-list-bare">
      <li class="bo-form-section">
        <p><strong>WO-4471</strong> · Hydraulic pump assy</p>
        <p class="bo-byline bo-byline--compact">Line 2 · due 28 Aug</p>
        <button class="bo-btn bo-btn--sm bo-btn--secondary"
                type="button" popovertarget="kb-menu-1">Move ▾</button>
        <div class="bo-dropdown__menu" id="kb-menu-1" popover>
          <button class="bo-dropdown__item" type="button">Move to In progress</button>
        </div>
      </li>
    </ul>
  </div>
</section>

<script type="module">
  import { initDropdowns } from "@busy-office/ui/js";
  initDropdowns();
</script>

Anatomy

  1. Lane — a widget, one per stage, laid out in a horizontally-scrolling cluster. A lane's count badge is the monitoring signal for that stage.
  2. Card — a plain form-section box reused as card chrome; identity + the one or two facts that matter for this board (due date, blocked reason).
  3. Move action — a dropdown listing only the stages this card can legally move to next — never every stage, which would let a card skip steps a real process cannot skip.
  4. Done lane — cards lose their action; a completed card is a record, not a thing to act on again.

Data contract

RequestReturns / on failure
GET /boardevery lane's cards + counts in one response — an agent reads board state the same way the human sees it, no separate API
POST /cards/:id/move{ to: "in_progress" } — the card re-rendered in its new lane, both counts updated; 409 if the target stage is not legal from the current one (re-render the card where it is, with the reason)
legal transitionsthe SERVER decides which "Move to…" items a card's menu offers — the client never guesses the workflow, it renders what it was sent

The AI-manages / human-monitors split, stated: an agent moves cards through the identical POST a human's menu item calls — no separate automation path. The human's channel is the lane's own shape: card counts, which lane is growing, which card has aged in Blocked. That is the whole reason a board earns its place over a grouped list — the shape is read at a glance, and it must stay true for an agent's moves exactly as much as a human's.

States

StateWhat ships
Empty lane"No orders queued" text inside the lane — an empty widget body reads as broken, not empty
Empty boardthe DIFFERENT empty — every lane shows nothing because nothing exists yet, distinct from a filter excluding everything
Move rejected (409)the card stays in its lane, states why ("Cannot skip Blocked — resolve the shortage first")
Card aged past a thresholdthe byline gains a warning word ("Blocked 6h") — two-channel, same as the job monitor's stalled state
Very long lanethe lane scrolls internally past a height, never grows the whole board vertically past the viewport
No JSthe Move menu still opens — popovertarget is the native HTML Popover API, so a card's menu button works with no script at all. Without initDropdowns() the menu just isn't anchored to its button (no positioning at our browser floor, so it opens in the popover's default top-layer position rather than under the trigger) and it stays open after a click instead of auto-closing on selection. The "Move to…" items themselves have no click handler in this static demo either way — a real build would need a form/link per item for the move to complete without JS
