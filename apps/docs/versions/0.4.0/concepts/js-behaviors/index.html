JS behaviors

The framework is CSS-first, not CSS-only. 26 small behaviors (zero dependencies) cover what the platform can't do or what accessibility demands: each is a call-once init using document-level event delegation, so DOM swaps (HTMX, Alpine, anything) never require re-binding.

Keyboard support generated

The four behaviors that own their own key handling — everything else is native (a plain <input>, a native <dialog>'s own focus trap) or has no keyboard surface (delegation-only behaviors like alerts). Extracted from source, so it can't drift from what's actually wired.

BehaviorKeyDoes
initCombobox() ArrowDown / ArrowUp open the list (filtering first if closed), then move the active option; clamps at the ends
Enter commit the active option (dispatches bo:combobox-select)
Enter (list open, nothing active) swallowed, never submits the form; commits the sole match if there is exactly one
Escape close without changing the value (native popover light-dismiss)
Tab focus leaves the widget: the list closes and the active option clears
(focus after a commit) the committed text is selected, so typing browses the full list again
initDataGrid() ArrowRight / ArrowLeft / ArrowDown / ArrowUp move the cell cursor; clamps at the grid edges
Home / End jump to the first/last cell in the row; with Ctrl/Cmd, the first/last cell in the grid
Enter focus the cell's one interactive widget, if it has one
Escape return focus from a widget to its parent cell
initDialogs() Escape close (native showModal(); skipped if data-dismissible="false")
Tab / Shift+Tab cycle focus inside the dialog, wrapping at the ends (focus trap)
initTabs() ArrowRight / ArrowLeft move to the next/previous tab in a horizontal strip, wrapping; activates immediately
ArrowDown / ArrowUp the same, in a vertical rail (.bo-tabs--vertical)
Home / End jump to the first/last tab; activates immediately

The delegation model

Each init installs one document-level listener and resolves its target at event time; element-level listeners (a dialog's close handler) bind lazily on first use, tracked in a WeakSet — never serialized into the DOM. What you can rely on:

  • Triggers may render before their dialog exists.
  • Swapped-in content works without re-init.
  • Clone / morph swaps can't strand stale state.

Event wiring is swap-proof; derived state is re-computed. The one HTMX-aware line in core JS is the htmx:afterSwap event name a table container listens for:

// Bound table containers re-derive selection state automatically when an
// htmx:afterSwap bubbles through them. Any OTHER swap mechanism calls:
import { refreshDataTable } from "@busy-office/ui/js";
refreshDataTable(container);

// Only NEW containers swapped in later need re-binding:
document.body.addEventListener("htmx:afterSwap", (e) => initDataTables(e.target));

Intent events

Behaviors report user intent through DOM events — your code decides what to persist. The full generated list (name, target, when it fires, payload) is the intent-event index; it is look-up material, not something to read once.

State attributes generated

Two attributes, deliberately kept separate rather than merged into one lifecycle vocabulary — a component is either OPEN or BUSY, and conflating the two would make "is this dialog open while its save is in flight" unrepresentable in one value.

AttributeValuesMeans
data-state closed|current|done|open|pending|rejected structural: is this open or closed (dialog, offcanvas, dashboard cards, the motion module's collapse), or where a multi-step control is in its own sequence (stepper, approval-workflow's timeline). Same attribute name, two genuinely different domains — read it per component, never assume the full value set applies everywhere it appears.
data-loading true busy: an async request is in flight (button, data-table). The opt-in @busy-office/ui/css/htmx module bridges it onto HTMX's own request state — .htmx-request [data-loading] disables pointer events for the duration with no JS wiring on your part.

Where a component's states don't fit either shape, it gets its own attribute rather than overloading these two: data-row-state (dirty|error|warning) on data-table rows, data-day (closed|holiday|selected|today) on the calendar. A shared name across unrelated domains is a worse contract than two honestly different ones.

The Save sequence

The pattern behind every Save/Submit/Approve button in this framework's pattern catalogue, as it actually composes today — no dedicated "loading state" component, because the pieces above already cover it:

  1. Idle — the button reads "Save".
  2. Saving — your JS (or the HTMX bridge, for free) sets data-loading="true" and aria-busy="true" on the button, and swaps its text to "Saving…". Two channels: the text change is what a sighted user reads; aria-busy is what a screen reader announces. Neither alone is the contract.
  3. Saved (or Error) — clear both attributes and restore the button's resting label, or route to your error state (a field's aria-invalid, a summary, a toast — pattern- specific, not this button's job).

Deliberately no spinner icon or success checkmark on the button itself — a real, measured decision, not an oversight: an opacity-dimmed solid-fill button drops to roughly 3.24:1 text contrast (axe color-contrast), under the 4.5:1 minimum. The button's own visible channel stays the text swap plus cursor: progress; a spinner or checkmark belongs beside or inside the button as your own markup if the pattern wants one — the framework does not force a specific glyph onto every Save action.
