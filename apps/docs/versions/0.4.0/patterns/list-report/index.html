Pattern: list report

Who uses it: AP clerks, all day — the screen they live in. What "done" looks like: find the invoices that need action, act on them in bulk, and never lose your place. Composed entirely from shipped components; the data table page documents the table itself, this page documents the screen. Not for a single record's full detail — once a clerk opens one invoice to review or act on it alone, that screen is a record detail (or an object page for a richer one); list-report's job stops at finding and bulk-acting on rows, not deep-diving into one.

The rows and the bulk buttons are one <form>, which is what makes step 4 below work: Enter from any row checkbox runs the bulk action, so a selection thirty rows down is zero keypresses from acting instead of thirty-two. Only the safe action is type="submit" — Reject stays type="button", so implicit submission can never reach a destructive one.

Filtering: typed tokens, not a filter dialog

ERP users live in a handful of named views and rarely compose filters from scratch. So the ad-hoc case gets one search field that accepts typed tokens, and there is deliberately no adapt-filters dialog:

Filtering by status: pending × vendor: acme ×

Zero new framework surface: the field is a plain <input type="search"> and each active token is the .bo-chip that already ships. Reads as a sentence, stays keyboardable, and survives being bookmarked because it is all in the URL.

The parse contract is the server's

  • key:value where key is one your server recognises; everything else is free text.
  • An unknown key stays free text — it is not a token with no matches. A vendor genuinely called ref:99 must still be findable, so guessing is worse than not tokenising.
  • Multiple tokens are AND; free text searches the columns you choose. Both live in the single q parameter.
  • Each chip's remove control is a plain <a href> carrying q minus that token — removing a filter needs no JavaScript, and works with the back button.

Working implementation in examples/po-app: status:pending vendor:stark narrows to one row, dropping the status token widens it to six, and the chips track both.

Anatomy

  1. Filter bar — a plain <form> in a cluster with filter controls. Submits on Apply; Clear is a native type="reset".
  2. Toolbar (.bo-data-table__toolbar) — bulk actions appear only when rows are selected; the selection count is filled by initDataTables().
  3. Table (.bo-data-table--sticky-col) — sticky header, frozen select column, aria-sort on the sorted header, status badges carrying text, not just color.
  4. Footer — rows-per-page + pagination, or a load-more button; pick one and keep it (see Scaling).

Data contract

What the server must return for this screen to work — the HTMX/fetch boundary:

RequestReturnsSwaps into
GET /invoices?status=&cc=&q=&page=the <tbody> rows + an out-of-band footer#invoice-rows
POST /invoices/bulk-approvethe affected rows, re-rendered with new badges#invoice-rows
GET /invoices?page=nnext page rows (append) or a full replace#invoice-rows
any request, 5xx or timeoutthe Error state above (.bo-alert--danger + retry, last good rows kept); POST /invoices/bulk-approve failing per row is separate — still 200, the failure is the returned row's own data-row-state="error", not a transport-level errorunswapped; alert renders in place

Rows carry data-row-id so partial responses can target one row. Selection state is CLIENT state — a swap that replaces rows clears it, which is the honest behaviour after a bulk action. Filters belong in the URL query so a filtered list is linkable and survives reload.

Keyboard walkthrough

The path an AP clerk actually takes, with nothing custom bound:

  1. Tab into the filter bar, type, Enter to apply — a native form submit.
  2. Tab to the select-all checkbox; Space toggles the page's rows and announces the count via the live region.
  3. Tab through row checkboxes, Space to pick individual invoices.
  4. Enter from any row checkbox runs the bulk action — no journey back to the toolbar at all. That is native implicit form submission, not framework code: the rows and the buttons are one <form>, and focus stays on the checkbox you pressed. Without the form the toolbar is one Shift+Tab per row you passed plus two — thirty-two presses from row 30, which is what this page measured before the form was added.
  5. Sorting: the header is a real <button>, so it is keyboard-reachable and announced as a control — but sorting itself is your code. The framework ships none. Your handler sets aria-sort on the <th>; leaving a hardcoded aria-sort on a header that never sorts announces an order that isn't real.

The table deliberately does NOT take a roving tabindex — screen-reader table browse mode is worth more than 2-D arrow navigation on a read-mostly list (data-grid-nav is opt-in per table when a screen really is grid-first).

Print behaviour

ERP lists get printed and signed. The print layer repeats the table header on every page, never splits a row, drops the toolbar/pagination/filter chrome, and forces status colors so a badge survives a monochrome printer. Print the page to see it — no print-specific markup required.

Scaling notes

  • Rows: measured render costs (1k → 20k, including a 4× CPU throttle) are on the data table page. Past ~5k rows, paginate server-side — the framework has no virtualiser and does not pretend to.
  • Pagination vs load-more: pagination when clerks cite "page 3" and need a stable position; load-more for scanning feeds. Don't ship both on one screen.
  • Columns: past ~10, the frozen select column plus horizontal scroll carries it; consider a column chooser rather than shrinking type.
  • Languages: German column labels run ~35% longer — headers wrap by design, so verify at compact density in the longest locale you ship.
