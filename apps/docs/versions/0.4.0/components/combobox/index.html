Combobox

A single-select text field that filters a list as you type — for picking one value out of a longer list than a plain select reads well, without the overhead of asking "which of these N do I want" up front. Not for a short fixed list — five or fewer known options is exactly what a plain select is for: no filtering to write, no JS to ship, and the platform's own picker is faster to operate. For picking several values, use the multi-select dropdown instead — different job. Without the JS: this one does not degrade — it stops. The listbox is a [popover], so Esc and light-dismiss are native, but opening, filtering and selection are all initCombobox()'s, and without it you have a text input beside a list that never opens. If you cannot run the behavior, ship a <select>.

Basic

  • CC-1180 — Warehouse
  • CC-2205 — Logistics
  • CC-4021 — Procurement
  • CC-3390 — Facilities

<div class="bo-form-field" style="margin-block-end: 0">
  <label class="bo-form-field__label" for="demo-cb-input">Cost center</label>
  <div class="bo-combobox">
    <input class="bo-input" type="text" role="combobox" id="demo-cb-input"
        aria-expanded="false" aria-controls="demo-cb-list" aria-autocomplete="list"
        autocomplete="off" placeholder="Search cost centers…" />
    <ul class="bo-combobox__listbox" id="demo-cb-list" role="listbox" popover>
      <li class="bo-combobox__option" role="option" id="demo-cb-opt-1" data-value="CC-1180">CC-1180 — Warehouse</li>
      <li class="bo-combobox__option" role="option" id="demo-cb-opt-2" data-value="CC-2205">CC-2205 — Logistics</li>
      <li class="bo-combobox__option" role="option" id="demo-cb-opt-3" data-value="CC-4021">CC-4021 — Procurement</li>
      <li class="bo-combobox__option" role="option" id="demo-cb-opt-4" data-value="CC-3390">CC-3390 — Facilities</li>
    </ul>
  </div>
</div>

Type to filter (case-insensitive substring match against each option's full text — try "log" or "cc-33"), ↓/↑ to move through the filtered results, Enter to commit. The listbox is a real [popover] — Esc and clicking outside close it without changing the field's value, for free. Two honest caveats (owner test report, 2026-08-16): the popover is never clipped by a scroll container, but it is positioned once at open time and is not re-anchored — so the list closes on scroll rather than drifting away from its field; and aria-expanded is resynced on the listbox's toggle event, so a test must assert after a task, not synchronously in the keypress.

No matches — the list closes, the field tells the story

When the filter matches nothing, the behavior closes the listbox (aria-expanded="false") rather than showing an empty popup — the typed text stays in the field. If "must match a known value" matters, validate on commit/submit: pair the field with the standard error message ("Unknown cost center") or the validation summary — don't invent an in-popup empty state the pattern doesn't have.

WAI-ARIA APG combobox pattern, not a custom widget

The input carries role="combobox", aria-expanded, aria-controls, and aria-autocomplete="list"; the popup is a real role="listbox" with role="option" children. initCombobox() keeps aria-activedescendant in sync as the active option changes — nothing is simulated with generic <div>s. On commit, it fires bo:combobox-select (detail: { value, text }) — your code reads e.detail.value for the machine value (data-value on the chosen option) and persists it (a hidden input, a form submit, an hx-patch).

Pick one, then inspect the DOM: the widget carries data-name="cost_center", so committing writes <input type="hidden" name="cost_center" value="CC-1180"> inside it. A plain form POST now sends the machine value, not the display label — no JavaScript of your own, no framework.

<script type="module">
  // "must match a known value" — the list has just closed on focusout,
  // so this is the natural moment to validate.
  document.addEventListener("focusout", (e) => {
    const input = e.target.closest?.('[role="combobox"]');
    if (!input) return;
    const hidden = input.closest(".bo-combobox").querySelector('input[type="hidden"]');
    const ok = input.value === "" || (hidden && hidden.value);
    input.setAttribute("aria-invalid", String(!ok));
  });
</script>

Validation for "must match a known value": the field can hold free text the user typed, so check it on focusout — the list has just closed, which is the natural moment. Server-side, treat the hidden value as authoritative and re-render with aria-invalid if it is missing.

Filtering semantics

Exactly what the built-in filter does, so you can predict it: case-insensitive, single substring, matched against the option's full text content, with the query trimmed. It is not token-based (cc warehouse matches nothing), not accent-folded (zurich does not match Zürich), and not fuzzy. When you need more, own the filter: hide and show options yourself on input — the behavior only ever considers non-hidden options, so your matcher composes with its keyboard and ARIA handling.

// Own the matcher — the behavior only navigates options that are not hidden
const fold = (t) => t.toLowerCase().normalize("NFD").replace(/[\u0300-\u036f]/g, "");

document.addEventListener("input", (e) => {
  const input = e.target.closest?.("[role=combobox][data-custom-filter]");
  if (!input) return;
  const words = fold(input.value).split(/\s+/).filter(Boolean);   // token-based
  for (const li of input.closest(".bo-combobox").querySelectorAll("[role=option]")) {
    li.hidden = !words.every((w) => fold(li.textContent).includes(w));
  }
});

Async / server-driven options

The common ERP case: too many options to ship up front. Fetch on input, replace the <li>s, and let the behavior keep doing keyboard and ARIA. Ids are minted automatically if you omit them, so a template render is safe.

<script type="module">
  import { initCombobox } from "@busy-office/ui/js";
  initCombobox();

  const input = document.querySelector("#vendor");
  const list = document.querySelector("#vendor-list");
  let seq = 0;

  input.addEventListener("input", debounce(async () => {
    const mine = ++seq;                       // ignore out-of-order responses
    list.innerHTML = option("Searching…", { disabled: true });
    try {
      const res = await fetch("/vendors?q=" + encodeURIComponent(input.value));
      if (mine !== seq) return;               // a newer keystroke already won
      const vendors = await res.json();
      list.innerHTML = vendors.length
        ? vendors.map((v) => option(v.name, { value: v.id })).join("")
        : option("No matches", { disabled: true });
    } catch {
      if (mine !== seq) return;
      list.innerHTML = option("Search unavailable — retry", { disabled: true });
    }
  }, 200));

  // ids are minted by the behavior if you omit them, so a template
  // render is safe; aria-disabled rows are skipped by the arrows.
  function option(text, { value, disabled } = {}) {
    return "<li class='bo-combobox__option' role='option'"
      + (value ? " data-value='" + value + "'" : "")
      + (disabled ? " aria-disabled='true'" : "")
      + ">" + text + "</li>";
  }
</script>

Three parts make a row recognisable: __option-code (the ID, monospace and tabular), __option-label (the name) and __option-meta (one context column). All three sit inside the option, so the substring filter matches on any of them — typing 4021, Assembly or Production all find the same row. The label is what gets committed to the field; data-value still carries the machine value to the hidden input. A plain-text option behaves exactly as before.

Group headings describe the unfiltered order, so they disappear the moment you type — once results are ranked by match, a "Recent" heading above them would be a lie.

JS required Required: initCombobox() — without it the field is a plain text input; typing does not filter or open the list.
  • Single-select only — the committed value lives in the input's text, not on any option (options never carry a persisted "chosen" marker across reopens). For choosing several values, use the multi-select dropdown instead.
  • The listbox is a native [popover] — never clipped by scrolling containers, and Esc/light-dismiss close it without touching the field value at no extra cost. It is NOT re-anchored on scroll (CSS anchor positioning is below the browser floor), so it closes instead.
  • Focus leaving the widget closes the list and clears the active option — that is also the natural moment to run "must match a known value" validation.
  • Options carrying aria-disabled="true" are shown but skipped by the arrows and rejected by Enter and click.
  • Options rendered without an id get one minted at activation time, so aria-activedescendant is never an empty string.
  • Filtering is a case-insensitive substring match against each option's full text, computed client-side against the options already in the markup — for a server-driven / async result list, swap the options' hidden state yourself in response to your own fetch instead of relying on the built-in filter.
  • Commit dispatches bo:combobox-select with { value, text } — value comes from the chosen option's data-value (falls back to its text if absent).
