Inline editing

Editing values in place, inside a data table: seamless cell inputs, per-row dirty state, Save/Cancel, and the events your app persists with. The component-level how-to — the assembled screen, with its data contract and states, is the editable grid pattern. Not for creating a record — in-place editing assumes the row already exists and that each change is a small correction to it. A new record usually has required fields, validation that spans several of them, and a decision the user can abandon; that belongs in a detail form or a wizard, where Cancel means nothing was created. An empty row waiting to be filled in a grid gives the user no way to say "actually, never mind".

Inline edit — seamless inputs in cells

ItemQty
Widget A
Widget B

The cell is always a real input (.bo-input--seamless): it reads as text until hover/focus, so keyboard and screen-reader semantics never flip between display and edit modes. Persist with a form submit or hx-patch on change.

Multi-row inline edit — dirty state + save/cancel

This is the simple starting point of the editable-table path — plain cells, dirty badge, Save/Cancel. The graded continuation (combobox lookup cells, every cell type, realtime totals, save-per-change, a full PO line-items editor) lives on the Editable grid pattern.

ItemQtyActions
Widget A Unsaved
Widget B Unsaved

Same seamless input as above, plus data-row-edit on the table: typing marks the row data-row-state="dirty" (amber tint, same visual channel the error row state uses) and reveals that row's badge + Save/Cancel. Cancel resets the row's inputs to their last-saved value; Save dispatches a bo:row-save event with the row and its data-row-id — your code persists it (fetch, hx-patch, form submit), this behavior only tracks dirty state. Try it: edit a quantity below.

Choosing the editing design

Three editing designs ship, split by what the screen's job is — pick by context, not by taste:

The screen's job Design Why
Entry — the user came to fill things in Bordered fields: a form (detail-form) or an editable grid (editable-grid) The border is the affordance — when entry is the job, every enterable cell should say "you can type here"
Reading — corrections are occasional Seamless cells + row Save/Cancel (this page; detail-form's field-per-row variant) The value reads as a fact until touched; chrome would shout "form" at a screen that is a record
Entry, but it must LOOK like the read view The editable grid's WYSIWYG variant — every control seamless Display-identical at rest, affordance on hover/focus; the control never swaps, so keyboard and screen-reader semantics never change

Per field type (date, number, money, quantity), the field matrix names the exact control for each of these contexts. Save timing is the second, independent axis: batched per row (Save/Cancel, the default here) when a row is a unit of work, or per-change (data-row-edit="live") when each commit stands alone.

Markup — multi-row inline edit

<table class="bo-data-table" data-row-edit>
  <thead><tr><th scope="col">Item</th><th scope="col" class="bo-data-table__col--numeric">Qty</th><th scope="col"><span class="bo-visually-hidden">Actions</span></th></tr></thead>
  <tbody>
    <tr data-row-id="WIDGET-A">
      <td>Widget A</td>
      <td class="bo-data-table__col--numeric">
        <input class="bo-input bo-input--seamless bo-input--numeric" value="12" aria-label="Quantity for Widget A" />
      </td>
      <td class="bo-data-table__row-edit-actions">
        <span class="bo-badge bo-badge--warning" data-row-edit-dirty hidden>Unsaved</span>
        <button class="bo-btn bo-btn--sm" type="button" data-row-edit-save
                aria-label="Save — Widget A" hidden>Save</button>
        <button class="bo-btn bo-btn--sm bo-btn--secondary" type="button" data-row-edit-cancel
                aria-label="Cancel — Widget A" hidden>Cancel</button>
      </td>
    </tr>
  </tbody>
</table>
