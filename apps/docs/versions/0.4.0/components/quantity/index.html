Quantity

A count field, not a currency one — see Money for that. A real type="number" input, optionally joined to a unit select and optionally flanked by stepper buttons; min/max/step are native attributes, so validation, keyboard behavior, and any buttons' clamping all read from the same source of truth. Not for a number that isn't a count — a percentage, an index, a value with no meaningful unit or step: the joined unit field and stepper buttons imply affordances that number doesn't have, and a plain .bo-input--numeric is the honest answer.

The rule for this family: displaying a value is Amount's job; capturing one is Money's (currency) or Quantity's (count). One display component for every numeric value; two entry components, split by what the value is — and when it is neither a selectable currency nor a steppable count (a rate, a fixed-currency price, a percentage), a plain .bo-input--numeric is the whole answer: no fourth component, just the input modifier.

Basic — ( qty | unit )

View code 
<!-- desktop-first: no buttons, unit joined — the mirror of Money's ( currency | amount ) -->
<div class="bo-quantity">
  <input class="bo-quantity__input" type="number" value="2.50" min="0" step="0.01" inputmode="decimal" aria-label="Quantity" />
  <select class="bo-select bo-quantity__unit-select" aria-label="Unit">
    <option>kg</option>
    <option>g</option>
    <option>each</option>
  </select>
</div>

A quantity input joined to its unit select — the exact mirror of the Money field's ( currency | amount ) shape, and the natural desktop form. ↑/↓ and typing work natively; initQuantity() makes precision follow the selected unit (kg 2.50 → each, step flips to 1). No stepper buttons needed — they're the opt-in touch affordance, next section.

With stepper buttons — touch & warehouse

View code 
<div class="bo-quantity">
  <button class="bo-btn bo-btn--secondary bo-quantity__step" type="button" tabindex="-1" data-quantity-step="-1" aria-label="Decrease quantity">&minus;</button>
  <input class="bo-quantity__input" type="number" value="4" min="0" max="99" step="1" inputmode="numeric" aria-label="Quantity" />
  <button class="bo-btn bo-btn--secondary bo-quantity__step" type="button" tabindex="-1" data-quantity-step="1" aria-label="Increase quantity">+</button>
</div>

Requires initQuantity() — without it the buttons are inert, but the input itself still works (native number keyboard behavior, and it's a real form field either way). The buttons are pointer/touch affordances (warehouse gloves, tablets): they carry tabindex="-1" and cost no tab stops, since ↑/↓ on the input already steps. With buttons present a __unit-select sits after the + with a gap rather than joining; the static text __unit span is deliberately never boxed — it's an annotation, not a control.

With a unit

kg
View code 
<!-- no stepper buttons — this section is about __unit, not touch input -->
<div class="bo-quantity">
  <input class="bo-quantity__input" type="number" value="12" min="0" max="500" step="1" inputmode="numeric" aria-label="Quantity" />
  <span class="bo-quantity__unit">kg</span>
</div>

__unit is optional, plain text — an ISO/standard unit (kg, m, L) or an app-defined custom UOM (box, pallet), same as Amount's __currency — no allowlist, just text.

Read-only display — use Amount

1,250 ea
View code 
<!-- a count, read-only: Amount with a unit -->
<span class="bo-amount">
  <span class="bo-amount__value">1,250</span>
  <span class="bo-amount__unit">ea</span>
</span>

There is no .bo-quantity--display. One existed briefly, purely to mirror this component's name, and no screen ever used one — every screen that shows a count uses Amount with its __unit part, which already aligns and tabulates every numeric value in a column. It was removed before it reached a release rather than kept for symmetry (grill 2026-08-19). The visual difference is the affordance: a bordered box says "you can type here", plain text says "this is a fact" — the two are meant to look unrelated.

Interactive unit — precision follows it

View code 
<!-- no stepper buttons — this section is about the unit select driving
     precision, not touch input; the desktop-first (joined) shape composes
     with __unit-select exactly like it does with __unit -->
<div class="bo-quantity">
  <input class="bo-quantity__input" type="number" value="2.50" min="0" step="0.01" inputmode="decimal" aria-label="Quantity" />
  <select class="bo-select bo-quantity__unit-select" aria-label="Unit">
    <option>kg</option>
    <option>g</option>
    <option>each</option>
    <option>box</option>
  </select>
</div>

Swap the static __unit span for a real <select class="bo-select bo-quantity__unit-select">: changing unit re-derives the input's step/decimals from the built-in unit table (kg 2.50 → each 3 → g 3.00) and reformats the value — the same mechanics as the Money field's currency select. data-decimals on an option or the container overrides the table.

Fractional units — step IS the precision

kg
View code 
<!-- fractional units (weight, volume, time) need a decimal step AND
     inputmode="decimal" — "numeric" implies an integer-only keypad on mobile.
     No stepper buttons — this section is about step/precision, not touch input. -->
<div class="bo-quantity">
  <input class="bo-quantity__input" type="number" value="2.50" min="0" max="500" step="0.25" inputmode="decimal" aria-label="Quantity" />
  <span class="bo-quantity__unit">kg</span>
</div>

Whole-count units (ea, box) use step="1" with inputmode="numeric"; fractional units (weight, volume, time) need a decimal step — 0.25, 0.01 — AND inputmode="decimal", since numeric implies an integer-only keypad on mobile. There is no --decimals modifier — a static field's precision is the step you write; a __unit-select field derives it from the built-in unit table below, with data-decimals overriding either way.

Grouped display — data-grouped

ea each
View code 
<!-- data-grouped: a large stock count reads as 1,250,000 —
     grouped ON BLUR; the generated hidden input submits the raw number. -->
<div class="bo-quantity" style="max-inline-size: 16rem"><!-- the default
     12rem cap fits "9,999"; a grouped 7-digit count needs more room -->
  <button class="bo-btn bo-btn--secondary bo-quantity__step" type="button" tabindex="-1" data-quantity-step="-1" aria-label="Decrease quantity">&minus;</button>
  <input class="bo-input bo-quantity__input" type="number" inputmode="numeric"
      value="1250000" min="0" step="1" name="stock-count" data-grouped
      data-locale="en-US" aria-label="Quantity">
  <button class="bo-btn bo-btn--secondary bo-quantity__step" type="button" tabindex="-1" data-quantity-step="1" aria-label="Increase quantity">+</button>
  <span class="bo-quantity__unit" aria-hidden="true">ea</span>
  <span class="bo-visually-hidden">each</span>
</div>
<!-- + initGroupedNumber() once, alongside initQuantity() -->

Warehouse-scale counts group their thousands on blur — the steppers keep working on the machine value, and the generated hidden input submits the raw number. The same mechanism as Money's grouped amount (one behavior, three controls); locale comes from data-locale, precision from step or data-decimals as everywhere else.

Unit decimals reference — the complete built-in table

Every unit the built-in table knows, case-insensitive. Anything not listed leaves the field's precision entirely alone — real master-data UOM codes (MT, ltr, cbm, bundle…) are almost never these exact strings, and an unknown unit must never rewrite your value (Slice 19 hardening: the earlier default-0 silently rounded fractional quantities). Unlike currencies there is no ISO-closed list of units, so this is a pragmatic common-ERP set — your data-decimals override extends it per field without waiting for the table.

In a line table, split the pair: the unit is its own column, fixed per row, and each qty cell is just the input — no unit-select, no steppers. step/ inputmode are server-rendered per that row's unit (whole ea vs fractional kg here). The joined ( qty | unit ) control is the form shape — it belongs in a cell only in the rare case the user must change a row's unit inline; steppers belong on touch screens, not dense line grids.

Large-target (warehouse-floor) variant

View code 
<div data-density="spacious">
  <div class="bo-quantity">
    <button class="bo-btn bo-btn--secondary bo-quantity__step" type="button" tabindex="-1" data-quantity-step="-1" aria-label="Decrease quantity">&minus;</button>
    <input class="bo-quantity__input" type="number" value="4" min="0" max="99" step="1" inputmode="numeric" aria-label="Quantity" />
    <button class="bo-btn bo-btn--secondary bo-quantity__step" type="button" tabindex="-1" data-quantity-step="1" aria-label="Increase quantity">+</button>
  </div>
</div>

There's no separate "large" modifier — density IS the size variant. data-density="spacious" (44px controls) already meets the WCAG 2.5.8 minimum target size; scope it to a warehouse-floor screen the same way you'd scope compact to a dense table.
