Data table

Check a row — the bulk-action toolbar appears via :has(), zero JS. Sticky header, tabular numerals, density-aware row heights, container-query auto-compaction below 480px container width. Two tiers, same markup family: Simple (below) covers selection/sort/filter for free; reach for Advanced (data-grid-nav + initDataGrid(), further down this page) only when a screen genuinely needs full two-axis keyboard navigation — most tables don't. Not for laying out a page — a table means "these rows are the same kind of thing, and these columns are the same fact about each". Using one to place a form's labels beside its controls, or to put two panels side by side, tells a screen reader there is tabular data to navigate when there is none. Those want form sections and the layout primitives. A single record's own facts are not a table either — that is key-value facts, which is one thing described, not many things compared.

Performance at scale — measured, not guessed

Measured 2026-08-15 against the full table stack (sticky header, row checkboxes, badges, container query, initDataTables()) in the examples/po-app stress harness (/stress?n=…):

RowsInitial renderSelect-allPost-bulk-check style flush
1,00085 ms4 msnegligible
5,000174 ms18 ms231 ms
20,000558 ms49 ms610 ms
5,000 4× CPU throttle1,625 ms15 ms174 ms
20,000 4× CPU throttle3,783 ms60 ms686 ms

The 4×-throttle rows approximate older corporate hardware (added after the decisions grill challenged the single-machine evidence). Render and scroll scale linearly with no cliff; the recurring cost is the bulk-select style recalculation (the selected-row tint re-evaluating per row) — it repeats on EVERY bulk toggle, staying under 700 ms even throttled. The genuine pain point is initial render at 20k rows on slow hardware (~3.8 s). Practical guidance: a few thousand rows are fine as-is; beyond that, paginate server-side (page numbers or load-more) — which dense ERP screens want anyway for findability. There are no virtualization hooks: windowing breaks Ctrl-F, select-all semantics, and screen-reader row counts, and pagination is the answer at the scale where tables stop being scannable. Re-open condition, not dogma: if a real deployment measures interaction costs breaching ~1 s at row counts it genuinely cannot paginate, the /stress harness in examples/po-app is kept for exactly that re-measurement.

The scroll container is the focusable element (tabindex="0" with an aria-label), so a keyboard user is not stranded behind fifty tab stops: focus the region and the arrow keys scroll it. Measured, because "reachable" is not the same as "usable": each press moves about 40px, so the fiftieth column is roughly 76 presses away, and End does not help — this container scrolls horizontally only, and End acts on the vertical axis. Reachable, then, but tedious by any honest reading, which is the next argument for the column chooser below rather than a defect to paper over.

Fifty visible columns is usually a symptom, and this page will say so rather than just prove it renders. Nobody reads fifty columns; they read the twelve their job needs. The ERP answer is a column chooser plus saved views — let each role pick its columns once and store the choice, so Purchasing sees prices and the warehouse sees bins. Ship the wide table as the source of those views, never as the default screen. If you genuinely need all fifty at once, that is a report or an export, not a screen — see the Excel round-trip.

Multiple frozen columns

--sticky-col above freezes ONE column for free — its offset is always 0, no JS needed. Freezing a second or third column needs each earlier column's actual rendered width, which nothing knows in advance (columns size to content by default) — so this is the one case in this page's table story that opts into JS: data-sticky-cols="2" plus initStickyCols(), which measures the header row and keeps the offsets live across resizes. Capped at 3 columns — freezing more than that is usually a sign the table needs a column chooser, not more frozen columns.

Right-click column menu

data-context-menu opens the SAME popover menu component initDropdowns() already renders for the toolbar's Columns picker — right-click a header instead of clicking a button, and the menu opens at the cursor. This behavior (initContextMenu()) owns exactly one thing: positioning. It doesn't own sorting or hiding — those menu items below call the exact mechanisms this page already documents (aria-sort for sort, data-col-toggle for hide), the same as clicking the existing sort button or toolbar checkbox would. A per-column filter item and a runtime "always visible" pin were graded out of scope for the framework — see .roundtable/ for the reasoning.
Acme Supply Co.$4,208.00
Globex Industrial$18,940.50

Right-click "Vendor" or "Amount" above. The Sort items are static here, the same way the "Simple" section's sort button at the top of this page is — wiring them to actually re-order rows is consumer code either way, on-page click or context-menu click makes no difference to that contract. "Show column" is real: uncheck it and the column disappears immediately, because it's the exact same data-col-toggle checkbox the toolbar pattern uses, just rendered inside a right-click menu instead of a toolbar dropdown — the menu's own markup has to live INSIDE the same .bo-data-table-container as the table for that to work (data-col-toggle's hide logic looks up its container via .closest(); a popover placed as a sibling after the container, which is where it would naturally land if authored after the closing <table> tag, silently finds no container and does nothing — caught live on this exact demo before it shipped).

No grouping component exists because none is needed — this composes from plain HTML table semantics the CSS already styles: one <tbody> per group, the group header a <th scope="rowgroup" colspan> row (bold by default; the scope declares it heads its <tbody> — screen-reader support for rowgroup association varies, so keep group names ALSO in prose/ captions when the grouping is load-bearing), subtotal and grand-total rows are ordinary rows using __col--right/__col--numeric. Proven in the examples/po-app "Spend by cost center" screen, both themes. Don't combine with --striped (stripes land arbitrarily on summary rows) or with row-select/sort (sorting across grouped bodies is your code's problem — regroup server-side instead).

Conditional cell tone

data-tone="danger|warning|success" on a <td> tints that one cell — subtle background plus an inset accent, same shape as row state above, scoped to a single cell instead of a whole row. The framework never decides why a cell is toned: a negative balance, a budget threshold, any business rule — that condition is computed server-side and rendered as this one attribute. Pair the tone with text that says the same thing (a sign, a word, a badge) — the color is not the only channel. Background is the default; add data-tone-text to also tint the text (the CC-1180 row below) — opt-in rather than automatic, since forcing text color on every toned cell would fight a value that's already bold or already colored by something else.

The bar on the leading edge — what it is for, and when to stop

The bar is not decoration, and that is the whole reason it is there. Under forced-colors (Windows High Contrast) the browser throws away background colours — so a tone carried by tint alone would vanish for exactly the readers who most need it. The bar survives, because the forced-colors rule swaps it to a real border-inline-start. Remove the bar and the tone becomes a single fragile channel.

It follows the leading edge, not the left: under dir="rtl" it flips to the right, one of the framework's six documented flip sites (see i18n).

When it is the right mark:

  • Row state — one bar on the row's leading edge, running down the margin like a change marker in a diff. This is what the idiom was built for and where it reads best.
  • A few exceptional cells — two or three cells in a table that break a rule. The bar draws the eye to something rare.

When to reach for something else:

  • When most rows have a toned cell, the bars stop being exceptions and become texture — the eye reads a ragged column of stripes instead of "look here". If a majority of rows qualify, tone is carrying ranking, not exception: sort by the value, or put the meaning in a badge the reader can actually read.
  • When the toned cell is a right-aligned number, the bar sits on the far side of the cell from the digits it qualifies. That is a real weakness of the shape and worth knowing before you reach for it; pair it with data-tone-text so the meaning also lands on the number itself.
  • Never as the only channel. Both the tint and the bar are colour. The programmatic meaning belongs in text — a sign, a badge, a visually-hidden phrase — exactly as the demo above does with its minus sign.

Column alignment

Put the same modifier on the <th> and every <td> in a column: --left, --center, --right, or --numeric (right-aligned and tabular figures, for amounts).

Column width & long content

Columns already size themselves to their content — the table never sets table-layout: fixed, so the browser's default column-width algorithm does the "fit the contents" work with zero CSS from this framework. What that algorithm doesn't do on its own is stop a column growing forever, and the fix has a real trap in it: max-inline-size on the <td> itself is silently ignored under table-layout: auto unless the row is already under width pressure — a table with room to spare just renders the cell at its natural width, max-width or not. Put the cap on an inner element instead (a <span> is enough) alongside the existing .bo-u-text-truncate utility — plain CSS, not a data-table-specific mechanism.

The full vendor name is still in the DOM — this is a visual clip, not a data loss, so a screen reader and Ctrl+F still see the whole string. Give the inner element a title attribute if the clipped tail matters enough to show on hover. examples/po-app's own Vendor column uses the bare <td> form without a fixed cap — that only truncates once the whole table is genuinely squeezed for space, which is a different, weaker guarantee than this section's deliberate cap; worth fixing there too, tracked as a follow-up rather than folded in silently here.

Nowrap without clipping. Sometimes a column shouldn't wrap OR truncate — it should just stay on one line and let the table grow wider instead. .bo-u-text-nowrap is that: plain white-space: nowrap, no overflow/ text-overflow. Wrapping is already the free default (no class needed) — this utility only exists for the opposite case. Because white-space is inherited, the SAME class works at either granularity: on one <td> it's column-scoped, on the <table> itself every cell inherits it — no separate "by column" vs "by table" mechanism.

The whole table has .bo-u-text-nowrap on it, so every cell — not just Status detail — stays single-line; the container's own horizontal scroll (already there for every table on this page) takes over instead of the row growing tall.

Font styling (bold, emphasis) is the same story: no utility class exists or is planned for it — a subtotal or grand-total row uses a real <strong> (see "Grouped rows + subtotals" above), which is both simpler and correct HTML semantics a screen reader can act on. Adding a bo-u-font-bold-style class would be a second way to do something native HTML already does — this framework ships "semantic components, not utility soup" on purpose.
