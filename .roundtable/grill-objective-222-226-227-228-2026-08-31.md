## §D — REFUTED: the grill's best candidate finding was already gated

This is recorded because it was the most promising thing found and it is wrong;
the refutation is the useful output.

`icon.astro` renders twelve **hand-typed glyph names** (`glyphs`, the editorial
eight, and `deprecatedGlyphs`) into `bo-icon--*` classes. 227.3's guard compares
a *count* (parsed 26 vs `api.json` 26), so a **rename** passes it: the count
never moves. The hypothesis was that renaming a glyph would ship a dead class to
a rendered page with nothing failing — the same "publishes rather than fails"
shape 227.3 had just fixed, one step over.

**Red-proved by injection, and the injection is what killed the hypothesis.**
`.bo-icon--doc` → `.bo-icon--doczz` in the source CSS:

```
core build            EXIT=0      # 227.3's guard does NOT fire
api.json variants     26          # count unchanged, as predicted
api.json has --doc?   false       # the name is gone
npm run docs:build    EXIT=1
  check-markup FAILED — 116 problem(s) across 165 file(s):
       unknown class "bo-icon--doc"
```

`packages/core/scripts/check-markup.mjs dist` runs in the docs build chain and
reconciles **every** rendered `bo-*` class against `api.json`. So glyph names
are guarded one layer up, by a gate written for a different reason (roadmap
32.2). The hypothesis is dead.

**Two injection-discipline notes, both this repo's own base rate landing again:**

- The first injection used `docZZ`, and the core build went red on
  **stylelint's naming pattern** — a red for the wrong reason, which is the
  mirror image of the green-red-proof trap. Re-run lowercase.
- The refutation then reproduced *by accident*: a later build failed identically
  because the core `dist/` still carried the injected `api.json` after the source
  had been reverted. Two independent firings of the same gate, one of them
  unplanned.

## §E — HELD AND FIXED: the one icon mirror no gate can see

`check:markup` reconciles class **names**. It structurally cannot see whether
the right glyphs are listed as deprecated, because a wrongly-listed glyph is
still a class the framework ships.

`deprecatedGlyphs = ['settings', 'barcode', 'building', 'user']` was hand-typed
against the four `/* DEPRECATED` blocks in the same stylesheet. Deprecating a
fifth glyph would have left the page showing it among the eight that "earned
their place", under a badge still reading 4, with nothing failing — and that set
is the page's published answer to *which glyphs should I stop using*.

**Fixed by derivation, not by refreshing the list** (217.2/220.1's rule): the
set is parsed from the shipped **unminified** css — minification drops the
comments that carry the deprecation — and reconciled against an independent
count of the markers themselves. No hand-typed floor, for 227.3's stated reason.

Red-proved in both directions, through the built page:

```
A. inject a stray "DEPRECATED" with no glyph selector after it
   markers=5, derived=4 (confirmed BEFORE the build)
   npm run docs:build  EXIT=1
   /components/icon/index.html  icon: parsed 4 deprecated glyph(s) from the
     shipped css, but it carries 5 DEPRECATED marker(s). …

B. inject a real DEPRECATED block above .bo-icon--close (not one of the eight)
   markers=5, derived=5 ["close","settings","barcode","building","user"]
   npm run docs:build  EXIT=0
   rendered badge 4 -> 5, and "close" enters the deprecated cluster
   (baseline page: badge 4, no "close" anywhere in that region)
```

With the stylesheet untouched, the rendered `/components/icon/index.html` is
**byte-identical** before and after the change — two full clean builds, diffed.
The derivation reproduces the hand-typed list exactly; what it removes is the
silence.
