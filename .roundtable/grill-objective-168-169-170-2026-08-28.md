### The part that would have been published wrong

The first reading split the log by era and reported **17% → 56%** grill-
dependence (3 of 18 crossings, then 5 of 9). That number is real and it is
misleading, because arming-set size is a confound: rule 3's threshold is three,
and a set of exactly three is dependent if it holds even one grill slice.

```
# controlled: crossings armed by EXACTLY 3 slices, the fragile regime
#   first 18 crossings: 5 such, 3 grill-dependent
#   last  9 crossings: 6 such, 5 grill-dependent
# size-independent: grill share of distinct arming slices  10% -> 17%
# mean arming-set size 5.3 -> 5.4 (median 4 -> 3)
```

**Controlled for size the effect is flat** — 3 of 5 then, 5 of 6 now, n far too
small to call a trend. What actually changed is that **minimal arming sets
became the normal case**: 5 of 18 crossings had exactly three armers, then 6 of
9. Grills run more often, so the counter sits in its most fragile regime almost
always, where one grill-derived slice decides the dispatch. That is a different
claim from "the loop is becoming more self-referential", and only the first is
supported.

**Counter-evidence, and it decides the action — no change.**

- Every argument 170.B gave still stands: rule 3 sits above rule 4 precisely so
  it cannot starve (five recorded starvations of that shape), and a heading
  classifier in the dispatcher would be the sixth regex — 170.B's own first
  attempt got 4 of 26 by missing the older heading convention.
- The follow-up work is real. 168.1, 169.3 and 170.1 are genuine items; a
  grill's children closing a slice is work closing.
- **The corrected analysis weakens the case for a mechanism, not strengthens
  it.** The headline that would have justified acting — an accelerating
  self-arm — does not survive the control.

**So: recorded, no item, no gate.** What is written down is the supersession of
"a first", annotated on Slice 170's entry in place, with the command. **What
would reopen it**: a third consecutive dependent crossing whose arming set

## B. The gate shipped one wake ago was tagged `@exact` while resting on a parser, and that parser FAILS OPEN — **Evidence** (demonstrated on the real file). Fixed in place.

`check-resume-charter.mjs` (169.3) declared:

> `@exact` — both halves are string membership over two files. There is no
> recognition step to fool, so no `--self-test` is owed.

True of assertion 1. **False of assertion 2**, which is membership over the
output of `headingsIn` — a state machine that has to decide which `#` lines are
headings and which sit inside a fence. The file's own comment anticipated this
(*"Left in, this is a recognition step — which would make the `@exact` tag above
a lie"*) and concluded that skipping fences removed the recognition. It did not;
it moved it.

**Demonstrated by running the parser, not by reading it.** The exported
`headingsIn`, copied verbatim into a probe:

| input | gate's verdict |
|---|---|
| real `RESUME.md` | green (correct) |
| `+ "## Cloud-wake toolchain — what works, in order"` | **red** (correct) |
| the same paste, preceded by one stray ` ``` ` line | **GREEN — missed** |
| the same paste, below a pasted recipe with a nested fence | **GREEN — missed** |

An unterminated fence leaves the state machine open, so every heading below it
is invisible and the loop of `g.check`s passes *by not looking* — while printing
"13 charter rules hold". `RESUME.md` is rewritten wholesale every wake and is
full of shell recipes, which makes it the document in this repo most likely to
carry an odd fence. This is CLAUDE.md's "a gate that cannot run must fail
loudly, never skip quietly", one level in: the gate ran, and silently checked
nothing.

**The base rate decided the fix, per 94.11's precedent.**

```
for f in $(grep -rl '@exact' apps/docs/scripts packages/core/scripts scripts); do

**1 of 39.** A predicate true of one file is not a class, so nothing was built

existing ratchet does the enforcing with no new machinery.

**Shipped in this wake** (it is smaller than explaining it, per LOOPS.md's
improvement rule):

2. `hasUnterminatedFence` exported, and asserted as its own loud `g.check` — the
