## A. Every slice in this window contained an instrument defect, and the instrument's own item is what found it — **Evidence** (3 of 3)

| slice | the defect | what found it |
|---|---|---|
| **163** | `staleOnce` was computed and **never printed** — a later edit in the same commit clobbered the loop that printed it. The used-once reconciliation was dead on arrival. | Red-proving both directions and getting **silence**. Nothing else would have. |
| **164.1** | The dispatcher's parser missed **9 rows, every one a `Continue` row** — exactly what both counters count — printing "982 iterations" against a raw count of 991. | Reconciling the parser's count against the raw bullet count, which that item then installed as a permanent check. |
| **165** | The archive-counting command attributes every line to the last `## Slice` heading, so a non-slice `## ` section is billed to the preceding slice. **Slice 29 read 78 lines while being a correct 3-line pointer.** | Running the command the item demanded be run, then looking at the one row that seemed impossible. |

**Three for three, and none was caught by a gate.** Each was caught by the wake
*using* the instrument, at the moment of use. That is not a new claim — CLAUDE.md
already calls "an instrument's first output is not evidence" a **base rate** —
but this window is the cleanest confirmation yet, because all three instruments
were written by earlier wakes of this same loop and had already shipped.

**Counter-evidence, and it is substantial.** All three were caught *before* a
wrong claim reached a summary, a gate or the owner. And 164.1 measured its own
blast radius rather than assuming it: replaying both parsers over **703
revisions** of the log, the row count differed on 79 and the OVERDUE/ok verdict
on **exactly one**. A defect rate of 3/3 with a damage rate near zero is a
process that is working, not one that is failing.

**What this does NOT support**: adding a gate. Two of the three defects are in
scripts that already print their own reconciliation, and the third (165's
counting command) is a throwaway snippet inside a roadmap item — gating a
snippet is the ceremony this file's own history keeps refusing.

## B. "Re-run the command first" paid off twice in one window — **Evidence**

Both 163.1 and 165.1 shipped with the same instruction: *the command is in this
item, re-run it, and a disagreement with the pinned number is the first thing to
report rather than something to write over.*

Both disagreed.

- **163.1**: agreed exactly (61/75/7/10). Reporting "no disagreement" is itself
  the convention working — it turns a silent assumption into a stated check.
- **165.1**: pinned `20 slices / 3,019 lines / 4,212`; read **21 / 3,125 /
  4,461**. And chasing the extra slice is what exposed finding A's third defect.

Recorded because grills mostly record failures, and this is a practice that
demonstrably works: **a number written next to its command is a number the next
wake can falsify.** A bare number is not.

**Counter-evidence**: two instances, both in items written by the same recent
run of wakes, so this may measure a fashion rather than a durable convention.
The test is whether items written a month from now still carry their commands.

## C. A direction whose next action is OWNER-ONLY leaves the loop with nothing on-direction to do, and no rule can notice — **Evidence**

164.3 established that every dispatchable item was about the loop's own
machinery, and asked the owner to pick a direction. The owner decided
(2026-08-28): **finish (a) — publish `create-ui`.**

The loop has advanced that direction **zero times since**, and it is not
idleness. `(a)`'s entire remaining step is `npm publish -w
@busy-office/create-ui`, which is owner-triggered by standing policy. The loop
*cannot* take it. So rule 4 did what rule 4 does — took the oldest open item —
and the window's work was 163.1 (a report script) and 165.1 (an archive sweep).

**Measured**: of the file touches in this window, the overwhelming majority are
`ROADMAP.md`, `STATUS.md`, `loop-log.md`, `RESUME.md`, `LOOPS.md`,
`dispatch_status.py`, `INDEX.md` and grill snapshots. The only consumer-facing
files touched are `create-ui`'s `README.md` and `package.json` — and those came
from an **owner call surfaced in conversation**, not from a dispatch.

**The structural point**: `LOOPS.md` mentions "direction" seven times and every
one is *direction as an input to triage* — "a new requirement, direction, or
constraint", "a process/direction change gets edited directly". **No rule tracks
whether the chosen direction is being advanced**, and none can distinguish "the
direction is blocked, and what remains is maintenance" from "healthy work".
Rule 8 halts only when *nothing at all* matches, which is never true while
maintenance exists — and maintenance always exists.

This is the same shape this file has recorded three times about counters: a
signal starving underneath a rule that is always true. One level up, the
starving signal is the **direction**, and the always-true rule is rule 4.

**Counter-evidence, and it matters.** Nothing here was wasted: the archive sweep
was overdue by the dispatcher's own signal, and 163.1 closed the bucket
principle 3 actually names. The complaint is not that the work was bad. It is
that the loop cannot *tell* it is off-direction, so it cannot say so — and
saying so is what rule 8 exists to do.

**Refused: a "direction" field, a dashboard, or a product-vs-machinery ratio.**
The ratio was explicitly retired one grill ago with *"not to be re-raised as a
new finding"*, and that retirement is correct — a ratio cannot tell maintenance
that unblocks product from maintenance that displaces it. The smaller, honest
change is in the fed-back item below: let the dispatcher *say* when the direction
is blocked, without changing what it picks.
