## A. A 2.6x disagreement between two instruments was settled by deferring to the one with no command — and the deference was right — **Evidence**

166.5 wrote a replay harness to answer *"how often does the counter cross 3 over
the whole log"*. It read **61**. `dispatch_status.py`'s own header publishes
**23** for the unchanged parser. 166.5 concluded:

> the harness cannot reproduce a published, red-proved number, so the harness is
> what is wrong, and an unreconciled number does not go into a comment

Refusing to quote an unreconciled number was correct. **The reasoning was not
available to check, and that is the finding.** What `--self-test` red-proves is
`slice_of`'s *classification* — 14 cases, both traps — not the crossing replay.
The 18/22/23/23 figures are an ad-hoc measurement from 161.4, published in the
script header and in `LOOPS.md` rule 3 with **no command recorded next to
them**. So a 2.6x disagreement was adjudicated by treating a bare number as an
authority it had not earned. That is roadmap 159's own rule — *write the command
next to the claim* — failing on the numbers used to settle whether another
instrument was lying.

**Settled here, with the command, by a third independent implementation.**
Replayed row by row (reset on every `Objective` row; a crossing is the
transition of the distinct-slice set from <3 to ≥3), truncated to the **996
rows** 161.4 measured against:

```
python3 - <<'PY'   # full script in this grill's commit; the four variants
import re
ROW=re.compile(r"^- (\d{4}-\d{2}-\d{2} \d{2}:\d{2}) · ([\w-]+) · ([\w-]+) · (.*)$")
BARE=re.compile(r"^([1-9]\d{0,2})\.\d+[a-z]?\b")
PROSE=re.compile(r"^Slice ([1-9]\d{0,2})(?:\.\d+[a-z]?)?\b",re.I)
TOP=re.compile(r"^([1-9]\d{0,2})(?::|\s+[—–-])\s")
rows=[m.groups() for m in map(lambda l:ROW.match(l.rstrip()),open('.roundtable/loop-log.md')) if m]
def replay(rows,pats,closes,strict=False):
    seen=set(); cross=0; already=0
    for _,loop,_,item in rows:
        if loop=='Objective':
            if (len(seen)>3 if strict else len(seen)>=3): already+=1
            seen=set(); continue
        if loop in closes:
            s=next((m.group(1) for m in (p.match(item) for p in pats) if m), None)
            if s:
                b=len(seen); seen.add(s)
                if b<3<=len(seen): cross+=1
    return cross, already
PY
```

| + Standardize | 23 | **23** | **24** |

Five published numbers, five exact reproductions. **The header is right and the
harness was wrong** — 166.5's verdict holds, and it now rests on a measurement
instead of on an unexamined authority.

**And the numbers have already gone stale, which is the cost of the missing
command.** Ten rows later the `+ Standardize` figure is **24**, not 23. Nothing
in the repo would have said so; a reader quoting `LOOPS.md` rule 3 tomorrow
quotes a number that stopped being true inside a day.

**Second instance in the same window, pointing the other way — the positive
control.** 162.1's sha count was published as *994 of 1,001* and was wrong: a
`[0-9a-f]{7}$` anchor silently dropped every row carrying an 8- or 40-character
abbreviation, including the four that wake had just written. It was caught
**within one commit**, and 162.1 says why: 159's rule forced the command to be
written next to the number, and writing it meant running it. Two numbers, one
wake apart, one rule — obeyed once, skipped once, and the skipped one is the
one still standing wrong.

**Counter-evidence.** 166.5's judgement was correct on the merits, and its
refusal to publish an unreconciled figure is exactly the discipline this repo
asks for — the alternative failure (quoting 61) would have been worse. The
crossing count is also not load-bearing: no rule reads it, it is context for a
threshold that was set by judgement. So the cost here is small and is stated as
small. What is not small is the shape: *an adjudication between two instruments
is precisely where the losing side's absence of a command should have counted
against it, and instead it counted for it.*

## B. There is a SIXTH convention, and the right answer is to leave it unparsed — **Evidence**

`LOOPS.md` rule 3 and `dispatch_status.py` both now say the log uses **three**
conventions. It uses four. 30 `Continue`/`Standardize` rows name their slice
**mid-text**, after an em-dash:

```
Skeleton + state (empty/error) components — Slice 6 item 1 · shipped 0242384
Demo-section ordering audit (Slice 6 item 10) — sample-before-code convention
```

`SLICE_BARE` is start-anchored, `SLICE_PROSE` is start-anchored, `SLICE_TOP` is
start-anchored; all three miss it. Eight distinct slices (3, 6, 7, 8, 14, 18,
22, 96) are invisible.

**And it should stay that way, which is the finding.** Measured before
proposing anything:

```
# 30 rows · 29 of them 2026-08-14 → 2026-08-16 · newest 2026-08-21 13:52
# adding a mid-text fallback moves the whole-log crossing count 24 -> 25
```

**One crossing in the log's entire history, and none in the last week.** The
convention died when rows started leading with their slice number. Widening a
sixth time would buy that one historical crossing and re-open the exact risk
166.5's first draft demonstrated — a looser pattern that reports MORE is not
self-evidently a fix; that draft would have read `4-tick sweep` and `4-seat
adversarial grill` as slice 4 across 18 rows and made the counter fire early.

This is a **positive control for `LOOPS.md`'s own conclusion** after the fifth
recurrence: *"the lesson is no longer 'widen the regex'."* The first test of
that sentence is a sixth convention, and the sentence holds.

**Counter-evidence.** The parser is still, strictly, blind, and a file that says
"three conventions" while four exist is the same species of false comment 166.3
corrected two items earlier in the same slice. The correction belongs in the
script, where whoever next touches the regex will read it — not as another
paragraph in the file the dispatcher reads every wake (see C).

## D. "It does not move the crossing count" was used to refuse one change and would have refused a correct one — **Evidence**

161.4 refused adding `Explore` and `Objective` to `CLOSES_A_SLICE` on a measured
criterion, stated in the script:

> Adding both to the set below changes the number of times the counter reaches 3
> over the whole log from 23 to 23 — they buy nothing, so they stay out.

Measured on the same log, **`SLICE_TOP` — the fix 166.5 shipped the next wake —
also moves the crossing count 23 → 23** (996 rows; 24 → 24 today). By that
criterion it buys nothing either, and it was correct to ship: its value is that
the live counter **agrees with the row that was just recorded**, which is the
only mechanism that has ever caught this parser (twice of five).

So the criterion is not wrong, it is **insufficient**: historical crossing count
measures *cadence*, and both of these changes were about *correctness*. Applying
a cadence test to a correctness change gives the right answer once by luck and
the wrong answer once by construction.

**Counter-evidence.** 161.4's refusal was still right — Explore and Objective
are excluded for a stated *definitional* reason (a spike graduates into the
plan; an Objective row resets this very counter), and the 23 → 23 was offered as
corroboration, not as the whole argument. The finding is about how the number
reads to the next wake, which will find it stated as the reason.
