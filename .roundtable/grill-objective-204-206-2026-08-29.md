## A. 204's own environmental premise went stale within the same day it was written — Evidence

204 measured, and stated as fact: *"headless Chrome 141 reports `(pointer:
none)` — not coarse, none... Six launch variants were tried and none moves
it."* Re-measured fresh, directly, not read off the file:

```
node -e "import('./scripts/browser-harness.mjs').then(async ({launchDocsBrowser}) => {
  const b = await launchDocsBrowser(); const p = await b.newPage();
  console.log('pointerIsFine:', await p.evaluate(() =>
    matchMedia('(hover: hover) and (pointer: fine)').matches));
  console.log('version:', await b.version()); await b.close(); });"
#   pointerIsFine: true
#   version: Chrome/151.0.7922.174
```

**Chrome 141 → 151, a ten-version jump, in the same session's runtime.**
Puppeteer's bundled Chromium auto-updates; nothing in this repo pinned it.
204's "none moves it" conclusion was correct **for Chrome 141** and is now
false for the browser actually running here — not because six launch flags
started working, but because a newer headless Chromium changed its default
pointer-capability report.

**The consequence is good news, verified rather than assumed.** `check:claims`
now reports **154 documented behaviours verified live**, with **zero** `NOT
VERIFIED` lines — the three previously-skipped button cases (mouse press,
keyboard Space, reduced motion) are live-testing again, automatically,
because 204.1's own fix branches on the LIVE `pointerIsFine` read rather than
a hardcoded fact. The self-healing design 204.1 shipped is exactly what
absorbed this drift with zero code changes required. That is the mechanism
working as designed, caught by re-measuring rather than trusting the prose.

**What is stale, narrowly**: the environment-description prose in 204's own
roadmap text and in `check-claims.mjs`'s inline comments ("headless Chrome
141 reports... six variants tried") now describes a browser version this
session is not running. Not a defect in the shipped gate — the gate never
hardcoded the fact, only described it in prose — but exactly the shape
CLAUDE.md's own doctrine warns about: an environment fact is a snapshot,
not a permanent truth, and this is the same class of drift `check:rtl`'s
`ENVIRONMENT.md` split was written to contain for OTHER environment facts.

**Counter-evidence, and why no gate is proposed.** The code path was already
correct — it branches on a live capability read, never a version string —
so nothing needs fixing there. A gate asserting "the Chrome version matches
what was last measured" would be pure ceremony (94.11: the property that
matters, whether the 3 press-claims run live or fall back cleanly to
`notVerified`, is already self-verifying on every run via the pass line's
own count). What's warranted is narrower: a one-line correction to 204's
own historical record, not a mechanism.
