## A. The instrument that DECIDES does not reconcile; the one that only mirrors does — **Evidence**

`rebuild_from_log.py` counts the raw thing in the source and refuses to write
when it under-parses:

> `991 bullet line(s) … but only N parsed into rows. The mirror would silently
> under-report — fix parse_log_line, do not write.`

`dispatch_status.py` reads the same file, and its output is what *chooses the
loop this wake runs*. It had no such check. Measured:

```
grep -c "^- " .roundtable/loop-log.md          # 991   the raw thing
python3 scripts/loops/dispatch_status.py       # said "982 iterations logged"
```

**Nine rows were invisible, and every one is a `Continue` row** — which is
exactly what both counters count. The cause is `(\w+)` where the mode can be
`owner-decision` or `owner-wishlist` (9 rows, all 2026-08-24). This is the same
shape of bug the file's own header records twice about itself, the second time
in capitals: *"THE COUNTER WAS BLIND FOR FIVE DAYS, and this is the third
recurrence."* It is the fourth.

**How much did it cost? Measured, by replaying both parsers over every revision
of the log** — because the interesting question is not how many rows were
missed but how often the *verdict* changed:

```
703 revisions of .roundtable/loop-log.md replayed with (\w+) and with ([\w-]+)
  row count differs on          79 revisions
  OVERDUE/ok verdict differs on  1 revision   (dc7ea4d, 2026-08-24 20:02:
                                               Standardize read 3/4 "ok"; it was 4/4)
```

**One in 703.** The honest reading is that this bug cost approximately nothing,
and saying so is the point — a grill that inflates a defect to justify the
round is the same failure as a detector that cannot fail. What is not
approximately nothing is the silence: the script printed a confident number
while blind, and it is the number the dispatcher acts on.

**A second instance, which is what makes this Evidence rather than one bug.**
`RESUME.md` has carried this defect as a "noticed, not chased" note for four
wakes, and the note says **six**:

> *`dispatch_status.py` reports fewer iterations than `rebuild_from_log` — its
> `ROW` regex requires `\w+` for both loop and mode, so six legacy rows do not
> match.*

It was **nine** at the commit that wrote it (`de0c814`, checked by re-running
both parsers against that commit's own copy of the log), and it has been nine
since 2026-08-24, when all nine landed within four hours of each other. A bare
count, with no command, wrong from the moment it was written, quoted forward
three more times. Slice 159 wrote the rule against exactly this — *"write the
command next to the claim"* — and it went into `CLAUDE.md` on 2026-08-27 19:43.
The note was re-copied after that.

**Counter-evidence.** The counters were never actually starved by this: the
missing rows are all four days old, the verdict moved once, and the dispatcher
did not obey the flag that once anyway (Standardize next ran seven Continue
rounds later, not four). And `rebuild_from_log.py` — the script that has the
reconciliation — got it because 159.2 was a P0 about that exact script, so the
doctrine was applied where a bug had just been felt, not uniformly. That is a
reasonable way to spend attention; it is just not a reason to leave the
deciding instrument unguarded.

**Fixed this wake** (`dispatch_status.py`): the character class, plus a
reconciliation against the raw bullet count that raises rather than prints. The
script's docstring said *"Exit status is always 0"* while already having one
`raise SystemExit` path, so that sentence was corrected too.

Red-proved four ways, with the injection confirmed each time — the new regex
asserted to match the injected row **and the old one asserted not to**, because
an injection the old parser also accepts proves nothing:

| case | result |
|---|---|
| untouched log | `rc=0`, 991 iterations (was 982 — the fix is visibly live) |
| a `Continue · owner-wishlist` row appended | counted: Standardize 2→3, Objective gains slice 999 |
| the OLD regex against the real log | `rc=1` — **the reconciliation goes red on the bug it was written for** |
| a row with a malformed date | `rc=1` |

**Refused: a writer-side guard in `record_iteration.py`** that round-trips each
line through both parsers before appending. Base rate is 9 rows in 991 (0.9%),
from one convention, and the mode field is deliberately free text — the reader
now fails loudly, and a second detector for the same defect is the ceremony
this repo keeps refusing (`skip-list forks`, `Related` labels, word counts).

## B. Two clocks write one log, and nothing records which — **Evidence** (latent)

`record_iteration.py` writes `datetime.datetime.now().strftime("%Y-%m-%d %H:%M")`
— naive local wall-clock, no offset. The owner's machine is UTC+08; this
container is UTC (`date` → `UTC`, `time.tzname` → `('UTC','UTC')`). Since the
routine was promoted to `/schedule` (Slice 162), both write into the same file.

Measured, by joining each row to its own commit's author date:

```
rows written at +08:00 : "2026-08-28 00:13"  ← commit 2026-08-28T00:09:37+08:00
rows written at +00:00 : "2026-08-27 17:58"  ← commit 2026-08-27T17:57:55+00:00

python3 - <<'PY'   # the command, next to the claim
import re
R=re.compile(r"^- (\d{4}-\d{2}-\d{2} \d{2}:\d{2}) · ([\w-]+) · ([\w-]+) · ")
t=[R.match(l).group(1) for l in open('.roundtable/loop-log.md') if R.match(l)]
print(len(t),"rows ·",sum(1 for a,b in zip(t,t[1:]) if b<a),"inversions")
PY
  # 996 rows · 3 inversions      (after this wake's own rows)
  #   2026-08-28 00:42 -> 2026-08-27 17:58
  #   2026-08-28 07:14 -> 2026-08-27 23:44
  #   2026-08-28 08:17 -> 2026-08-28 00:48   ← added BY THIS WAKE
```

Every inversion sits exactly on a cloud/local handover. The log's line order is
**correct** — it is true chronological order — and the timestamps are what
disagree with it, by up to eight hours.

*The count in this section was wrong when first written, and re-running the
command is what caught it.* It said "2 of 990 pairs": the numerator was measured
before this wake recorded anything (a third inversion has since appeared, from
this wake's own rows) and the denominator was arithmetic on the wrong row count
(982 parsed rows is 981 pairs, not 990). The number grows by one per handover,
which is why the command is written here and the count is not treated as a
constant. That this grill's own §A is about a stale number carried forward
without its command is not lost on it.

**Nothing decides on this today, and that was checked rather than assumed** —
all three consumers were read:

- `dispatch_status.py` — orders by list index, i.e. file order. Immune.
- `generate_status.py` — `ORDER BY id DESC`, i.e. insertion order. Immune.
- `rebuild_from_log.py` — the one true `ts` comparison,
  `row["ts"] >= VOCAB_ENFORCED_FROM`, against a cutoff of `2026-08-19 05:00`.
  Nine days stale, so an eight-hour skew cannot move a row across it.

So this is **latent**, and the finding is filed as latent. What makes it worth
recording anyway is that `CLAUDE.md` tells wakes to *query the mirror to steer
prioritization*, and the first natural prioritization query is time-ordered.
The record is the thing this project refuses to put in a database precisely
because a human reads and diffs it — and a human reading it now cannot tell
which of two rows happened first without opening `git log`.

**Counter-evidence, and it is substantial.** Nothing has decided wrongly; the
skew is invisible except at handovers, of which there have been two; and the
obvious fix (write an offset) changes the log's line format, which four parsers
and 991 existing rows depend on. That is a migration, not a typo — which is why
this is filed as a decision (164.2) rather than fixed in passing, and pointed at
162.1, whose whole subject is what two dispatchers sharing one queue costs. This
is a second cost 162.1 does not name: the first one cost a wake and was
self-detecting; this one is silent and lands in the record itself.

## C. Positive control — 159's new rule paid off in the next wake — **Evidence**

Slice 160's triage measured with a command and wrote the command into the item,
under the rule 159 had just written. Its finding was *"two populations"*:
consumer apps cited as UX precedent (8 mentions) and design systems cited as
evidence (45).

The build round re-ran that command instead of re-deriving it, and **the framing
was wrong: there are four.** Two more populations existed that the triage never
saw — an *interop hazard* class (11 mentions, where the product name IS the
reader's search term, so describing the mechanism makes a troubleshooting page
unfindable for the failure it exists to rescue) and an *attribution* class
(`tokens/scales.css` crediting the MIT palette). Three of the four were kept;
only the 8 UX-precedent mentions were scrubbed.

This is the mechanism working end to end, one wake after it was installed:

- the premise was a measurement → the command went next to it,
- the criterion said *"finding either population already compliant is a
  satisfying outcome"* → disagreeing with the premise was on-plan, not off it,
- re-running found a **structural** error (wrong number of categories), not a
  numeric one. A re-derivation would very likely have reproduced the same
  two-population framing, because the framing is what a reader carries forward.

The same round also found the real defect: the MIT palette credit lived only in
a generated CSS comment and was **absent from `packages/core/NOTICE`**. That is
a licensing gap in the published package, found by grilling a documentation
question.

**Second instance, so this is Evidence rather than one happy case.** 158's own
premise was re-measured under the same rule the same window and was also wrong —
107 documentation pages was 118, the median moved, and *seven* outliers were
*twelve*. Both times the re-measurement was cheap and both times the original
number was wrong in a way that changed what the item should do.

**Counter-evidence.** Two instances, both from the same three-day window, both
performed by wakes that had just written the rule and were primed to apply it.
The rule's durability is unproven; what is proven is that it works when
followed.

### Not filed as a roadmap item, deliberately

**A ratio like the one above has already been raised and RETIRED here**, and
`ROADMAP.md` says outright *"Not to be re-raised as a new finding."* F1, the
verification-to-product ratio, broke because its denominator (framework CSS
growth) went to zero, and zero CSS growth is the charter working — a metric that
reads "added no CSS" as failure would push toward adding CSS for its own sake.
That retirement is correct and this grill is not reopening it. The measurement
above is reported as corroboration and stops there; **no instrument, dashboard
or gate is proposed**, because a number nobody acts on is the busywork LOOPS.md
already refuses, and because `.roundtable/INDEX.md` exists precisely to make
"this was already grilled" findable before it is re-grilled.

**And the finding itself is not a new item either.** What it argues for is a
direction, and *"choosing a direction is structurally an owner call, not
something a loop can derive"* — this file's own words, from the grill that
predicted this state. Filing "pick a direction" as a numbered item a wake could
dispatch would misrepresent who can close it. It is written into the OWNER CALL
that already exists (Slice 112's direction call, answered once on 2026-08-26)
as a re-arming, with the measurement attached, and it goes to the owner in this
wake's report.

What a wake *can* do without a direction is the three dispatchable items, and
they are worth doing. The finding is only that finishing them leaves the queue
empty of product work, and that no rule in `LOOPS.md` will notice.
