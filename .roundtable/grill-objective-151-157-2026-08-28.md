# Objective grill — Slices 151, 154, 156, 157 (2026-08-28)

Dispatcher rule 3, fired at 4/3 slices. Scope is the four slices closed since
the last Objective grill (149/150/152, 2026-08-27). All four were **owner-input
driven**, which is itself the first thing worth noticing: this window contains
almost no self-directed work, so it grades how the loop responds to direction
rather than how it chooses.

Evidence gate as usual: a claim needs ≥2 independent instances to be
**Evidence**; a single instance is **Hypothesis**. Every finding carries its
counter-evidence.

---

## A. Accept criteria are being written with PREDICTIONS embedded, and the predictions are being falsified — **Evidence**

An Accept criterion is supposed to be a checkable definition of done. Twice in
this window, one was written as a *forecast of what a gate would say*, before
the gate was run — and both forecasts were wrong.

| slice | the criterion as written | what measurement said |
|---|---|---|
| 154.1 | "the CHANGELOG carries a **Breaking** entry — the documented row-edit markup contract changes shape, which the freeze-audit correction says is Breaking" | **Not breaking.** `row-edit.ts` guards the badge with `if (badge)`, so consumer markup that still renders one keeps working. Logged as Changed. |
| 157.2 | "the two RTL flip entries go with it — `check:rtl` counts flip sites and **DESIGN.md's count moves** in the same commit" | **The count did not move.** Six stayed six: the row stripe is still a flip site. What changed is what that site *covers*. |

**Why this is worse than a wrong guess.** Satisfying either criterion
*literally* would have produced a wrong artefact — a Breaking entry for a
compatible change, or an edited count that should not have moved. In both cases
the measurement was believed over the criterion, which is the right order. But
the criterion is the thing a future wake reads as the definition of done, and a
wake with less context might have "fixed" the count to match.

**Counter-evidence.** Two instances out of roughly a dozen criteria written in
this window, both caught, both corrected in the roadmap text with the
correction stated rather than quietly overwritten. The mechanism worked; the
wording is what failed.

**The rule this argues for**, and it is a one-word change in habit: *an Accept
criterion names the PROPERTY to verify, never the value it will have.*

- ✗ "DESIGN.md's flip-site count moves in the same commit"
- ✓ "DESIGN.md's flip-site count agrees with what `check:rtl` reports"
- ✗ "the CHANGELOG carries a Breaking entry"
- ✓ "the CHANGELOG entry matches the actual compatibility, with the reasoning"

The second form is satisfiable by measuring. The first is satisfiable only by
being right in advance, which is not what a criterion is for.

## B. Six instrument errors in one session — and **three were name-derivation**, which is a rule this repo already has — **Evidence**

CLAUDE.md calls "an instrument's first output is not evidence" a *base rate*
rather than a discipline problem. This window supports that with six, all
caught, none by review:

| # | error | what caught it |
|---|---|---|
| 1 | Both dist behaviors declare a top-level `let installed`; concatenating them into one classic `<script>` silently failed to install. The repro's first two runs measured nothing. | an **injection assertion** added deliberately |
| 2 | `--bo-color-text-default` does not exist (`--bo-color-text-primary` does); the bad reference fell back to inheritance silently | **re-measuring after the "fix" changed nothing** |
| 3 | `.bo-icon--close` invented; no such class | grep before build (`check-markup` would also have caught it) |
| 4 | Dark specimen rendered dark-on-dark locally — the file had no `<!DOCTYPE>`, so Chrome was in **quirks mode**, where tables do not inherit colour | testing under **published** conditions instead of `file://` |
| 5 | `docs:build` / `suite:check` / `suite:audit` reported "NOT in CI" — the grep matched **alias names** while CI invokes them under different names | asking *what would make this wrong* |
| 6 | An unresolved-token scan produced **6 candidates, 6 false** — 3 regex artefacts, 1 runtime-set token used with a fallback, 2 inside a `<pre><code>` sample | checking each candidate before reporting it |

**The sharp part is #2, #3 and #5: all three are name-derivation errors** —
guessing an identifier from convention instead of reading it from the source.
CLAUDE.md already carries that exact rule ("Derive names from the generated
source, never from a convention. Page slugs are not class names"), and it was
violated three times in one session **by an agent that had read it**.

So the rule is not the fix; it already exists and did not prevent recurrence.
What actually caught all six was *an assertion or a re-measurement*, never
recall. That is the same conclusion this file's own history reached about the
Objective counter — "make the silence impossible instead" of trusting careful
wording.

**Counter-evidence, and it matters.** All six were caught **before** anything
shipped. Zero reached a commit, a gate, or the owner. The error rate is high;
the escape rate is zero. A process that produces six caught errors is not
obviously worse than one that produces two uncaught ones — and #6 is the proof
the habit is working, because it was killed by the check rather than by luck.

**Refused: a gate for #2/#6.** The obvious response is "gate that every
`var(--bo-*)` resolves". Measured first, per this repo's own base-rate rule:
**65 distinct token references from docs source, 0 genuinely unresolved.** The
three that looked unresolved were `--bo-anchor-landing-offset` (set at runtime
by `anchor-nav.ts`, and used *with* a fallback), and two `--bo-palette-mist-*`
inside a code sample teaching consumers to define their own. The predicate is
uniformly true, so the gate would distinguish nothing — and my instrument for
measuring it was itself 6-for-6 wrong. Ceremony, refused.

## C. The loop BATCHES, and the owner had to stop it — **Hypothesis** (one clear instance)

In Slice 157 the loop made six distinct changes before any commit: two new icon
glyphs, `RowEditActions.astro`, eight markup instances, `row-edit.ts`'s
documented contract, a new guide section, and the start of the cell-edge
removal — which is a **different item**. The owner's response was *"don't
confuse. just put in the road map to update one by one."*

The correction was right and the revert was clean (the cell-edge work moved to
157.2 and landed separately, with its own red-proof). But the batching is worth
naming, because it defeats the thing this project relies on most: a commit that
does one thing can be reviewed, bisected and reverted; a commit that does six
cannot, and the roadmap item stops describing what actually happened.

**Counter-evidence.** 154 was a genuinely coupled change (the util and its only
caller) and was correctly one commit; 156 was one page; 155 was correctly
consolidated *into* one round after triage had wrongly split it. So the loop is
not uniformly over-batching — it batched once, on the slice where the owner was
iterating fastest, which is exactly where small commits matter most.

Hypothesis, not Evidence: one instance. **What would confirm it**: a second
slice where an unrelated item's work starts before the current one is
committed.

## D. What went RIGHT, and should not be lost

Recorded because a grill that only finds faults teaches the next wake to stop
doing the things that worked.

- **154 found a container the item did not name.** The roadmap named two
  hidden-container cases; building it turned up a third
  (`.bo-widget__collapse`) that fails *worse* — it clips rather than
  un-renders, so `.focus()` succeeds and focus lands invisibly. A fix scoped to
  the item as written would have looked complete and left the worst case live.
- **156 refused the owner's literal framing and was right to.** "Four device
  layouts" would have taught device-branched markup in a container-query
  framework. The owner's own refinement ("indicate whether layout can support")
  is what made the ask land, and the measurement then produced a finding
  nobody had predicted: crossing the 896px band gives `main` **171px more**
  room, not less.
- **155 was consolidated rather than executed as filed.** Triage had split it
  into two items; the Standardize round found they were one finding with a
  third, worse instance behind them (CI never ran `build -w create-ui` at all).
  Executing the roadmap literally would have fixed two symptoms and missed the
  cause.

The common thread: **all three came from re-deriving at build time instead of
trusting the written item.** That is the same instinct finding A asks for in
Accept criteria.
