## B — every container measurement behind 211.2 and 213 ran a different htmx than the app ships

The app pins one version; the container has exactly one, and it is not that one:

```
grep -n 'unpkg.com/htmx' examples/po-app/server.mjs
#   125:<script src="https://unpkg.com/htmx.org@2.0.4"></script>
node -p "require('./node_modules/htmx.org/package.json').version"     # 2.0.10
find . -name 'htmx.min.js'          # ./node_modules/htmx.org/dist/htmx.min.js  — the ONLY one
```

211.2 states its shim served `node_modules/htmx.org/dist/htmx.min.js`, so that
run is **2.0.10 against a page pinning 2.0.4**. 213's control — the one whose
whole purpose was removing the shim's confound — **does not record which htmx it
served at all**; it says only that it repointed the `<script src>` at a local
static server. There is exactly one local candidate, so it was 2.0.10 too.

**What this does and does not touch, stated separately.** 213's *defect
diagnosis* is untouched: `3250 vs 3299` is arithmetic over rendered row heights
(98 rows at 33px, 2 at 32.5px, first-row sample) and no htmx version changes it.
What it touches is the **timing** figures either side of it — 211.2's
`anchorShift > 2 in 14/20` and `12/20`, and 213's `0 in 40 of 40` — because
those are races against a fixed 150ms wait, and chunk-fetch timing is htmx's.

That matters because 211.2 reasoned explicitly about a timing confound
(*"the timing is not the shipped timing"*), and 213 then wrote that the confound
*"was named and removed rather than argued away"*. It was removed for
**interception**. The version divergence is a second confound, and neither slice
names it. Finding A is the mitigation: CI runs the real 2.0.4 and is green.

## C — 211.1's "the mechanism costs nothing" rests on a dependency of a different workspace

211.1 argues: *"`htmx.org` is already a dependency in `node_modules`, so the
mechanism costs nothing; the question is entirely whether the example should
stop demonstrating the CDN wiring."* Measured:

```
node -p "require('./package.json').workspaces"   # [ 'packages/*', 'apps/*' ]  — no examples/*
cat examples/po-app/package.json                 # dependencies: @busy-office/ui ONLY
ls -d examples/po-app/node_modules               # No such file or directory
grep -n '"htmx' apps/docs/package.json           # 51:    "htmx.org": "^2.0.10"
```

So `node_modules/htmx.org` exists **only because `apps/docs` declares it**.
`examples/po-app` is not a workspace, declares no htmx, and has no
`node_modules` of its own — its `package.json` describes it as a *"reference
consumer: installs `@busy-office/ui` from the packed tarball and uses ONLY
documented APIs"*, which is precisely the property that borrowing a sibling
workspace's dependency would break.

Option (a) is therefore not free. It costs a declaration (or a vendored file),
and the version it would resolve to today (**2.0.10**) is not the version the
page pins (**2.0.4**). This does not decide the owner's call; it corrects the
cost the call is being made on.

## D — 211.1's refusal premise is false: no docs page teaches the CDN wiring

This is the finding worth the wake. 211.1's recorded reason for **not** vendoring
is that it *"changes what the reference app teaches — a real consumer wiring htmx
from a CDN, **which is what `/getting-started/htmx` documents**"*.

Per CLAUDE.md, plain fixed strings first, count before context:

```
p=apps/docs/src/pages/getting-started/htmx.astro     # 270 lines
grep -c unpkg $p        # 0        grep -ci cdn $p          # 0
grep -c jsdelivr $p     # 0        grep -c 'script src' $p  # 0
grep -c install $p      # 0        grep -c 'npm i' $p       # 0

grep -rl unpkg apps/docs/src/ | wc -l   # 0 files
grep -rli cdn   apps/docs/src/ | wc -l  # 0 files
```

The page's single `<script>` (line 202) is its own behaviour block, not a
consumer snippet. What it actually documents is the **integration**: the opt-in
`@busy-office/ui/css/htmx` stylesheet, the swap recipes, and the
`initDialogs`/`initDataTables` wiring. It never tells a reader how to load htmx
by any route — CDN, npm or otherwise.

Repo-wide, `unpkg` survives in exactly one piece of live code:

```
examples/po-app/server.mjs:125          # the app itself
apps/docs/scripts/check-po-app.mjs:320  # a comment ABOUT server.mjs
# every other hit is ROADMAP.md / ROADMAP-archive.md / ENVIRONMENT.md bookkeeping
```

**The sentence admits a second parse, and the finding survives it.** Read
strictly, the relative clause's antecedent is *"a real consumer wiring htmx from
a CDN"*, and that is measurably not what the page documents. Read charitably —
"the app teaches the CDN wiring; `/getting-started/htmx` documents htmx
integration generally" — the page's half becomes true and the load-bearing half
does not change: the claim is still that vendoring would break something the
project **teaches**, and the only artefact carrying the CDN form is
`server.mjs:125` itself, which no page cites as an example of how to load htmx.
Under either reading, nothing a reader is directed to would lose a lesson.

So the CDN form is not a documented contract that vendoring would break. It is
an implementation detail of one example, referenced by nothing that teaches.
**Finding the premise false is what 211.1's own Accept calls a satisfying
outcome**, and the item stays OPEN because the product call — should the example
demonstrate CDN loading *deliberately*, as a thing the docs do not yet cover? —
is still the owner's. What changes is that it is now a decision to **add**
teaching, not to preserve it.
