## Finding A — `249.3`: "20 components floor at Chrome 99" is false as written; **25** do

The published sentence:

> **9 distinct floors across 40 components**, Chrome 99 → 119 — the label is
> worth printing precisely because it is not uniform, and **20 components floor
> at Chrome 99** where the framework floors at 119.

Everything in it reproduces except the 20:

```
node -e "const j=require('./packages/core/dist/floor.json');
const pc=j.perComponent, labels=new Set(), chromes={};
for(const v of Object.values(pc)){labels.add(v.label); chromes[v.floor.chrome]=(chromes[v.floor.chrome]||0)+1;}
console.log(labels.size, chromes, j.floor.chrome)"
# 9 { '99': 25, '105': 9, '114': 1, '117': 4, '119': 1 } 119
```

- 9 distinct labels across 40 components ✓
- Chrome range 99 → 119 ✓, framework floor Chrome 119 ✓
- **components whose Chrome floor is 99: 25**, not 20.

**Where the 20 comes from.** It is the size of the largest *full-label* group.
Three distinct labels share a Chrome floor of 99 and differ in their Firefox and
Safari numbers — the labels are not spelled here, because `check:floor` forbids a
hand-typed floor outside `ROADMAP.md` and it is right to (see Finding D); read
them from `floor.json`:

```
node -e "const j=require('./packages/core/dist/floor.json');
const g={}; for(const [k,v] of Object.entries(j.perComponent))
  if(v.floor.chrome==='99') (g[v.label]=g[v.label]||[]).push(k);
for(const [l,ks] of Object.entries(g)) console.log(ks.length, '|', l, '|', ks.join(','))"
# three groups, sized 20 (amount…tree-table), 3 (breadcrumb, prose, tree)
# and 2 (alert, approval-workflow)
```

20 + 3 + 2 = 25. So the number is a real count of a real set — it just is not the
set the sentence names. The sentence's own subject is the *label* ("the label is
worth printing"), which is how the slip survived review: the surrounding clause
is about labels and the predicate is about Chrome.

**Why it is worth correcting rather than shrugging at.** It is the only figure in
`249.3` that argues *why the per-component floor is worth shipping at all* — the
non-uniformity claim. Under-counting the largest bucket makes the spread look
wider than it is (25 of 40 = 63% at the framework's oldest floor, against 50%).
The direction of the error flatters the item.

**Corrected in place**, as the property rather than the value: the sentence now
says 25 components floor at Chrome 99 and that 20 of them share one full label.

## Finding C — Slice 254's `928×384` container reads **913**×384 here, and the 15px is a platform scrollbar, not a change

Slice 254's crop decision rests on four live measurements. Re-taken in this
container against the same built page (`/patterns/list-report/`, 1440×900), via
`browser-harness.mjs` + `serve-dist.mjs`:

| 254 claims | measured here |
|---|---|
| the first `[data-density="compact"]` match is a toolbar — a 30px box with zero rows | `FORM.bo-cluster`, **30px**, **0** `tbody tr` ✓ |
| `.bo-data-table-container` holds 14 rows | **14** ✓ |
| …at 928 × 384 | **913** × **384** — height ✓, width **−15** |
| the clip ends at the last row fully inside — 9 of 14 | **9** ✓ |

The 15px is fully explained and is deterministic, not noise:

```
main.bo-app-shell__main  overflow-y: auto
  offsetWidth 1216 − clientWidth 1201 = 15   ← reserved classic scrollbar
docs-main    = 1201 − 48 padding            = 1153
docs-content = 1153 − 208 (13rem rail) − 32 (gap) = 913
```

The docs shell scrolls `main`, not the document — `window.innerWidth -
document.documentElement.clientWidth` is **0** on this page, which is why the
usual page-scrollbar check finds nothing. Linux headless Chrome reserves a 15px
classic scrollbar inside that scroller; macOS overlay scrollbars reserve **0**,
giving `main` clientWidth 1216 → docs-main 1168 → docs-content **928**, the local
session's exact reading. `grid-template-columns: minmax(0, 1fr) 13rem` on
`.docs-main` (Gallery.astro:801) makes the rail fixed, so nothing here is
font-metric-dependent.

**Nothing is broken and nothing needs a fix.** What this is worth is the trap:
*any* cloud-wake measurement of a docs content-column width reads 15px narrower
than the same measurement on the owner's machine, and the difference will look
like a layout regression to a wake that has not been told. Filed in
`ENVIRONMENT.md`, which is the file for exactly this — the first two hypotheses
tried here (page scrollbar, font metrics) were both wrong and cost two probes.

**Method note, in this file's own doctrine.** The hypothesis was tested twice and
refuted twice before it was believed: `window.innerWidth −
documentElement.clientWidth` read **0** (no page scrollbar), and
`.docs-main`'s rail turned out to be a fixed `13rem` rather than content-sized
(so the font-metrics story was dead). The reading that settled it measures the
box that carries the constraint — `main`'s own `offsetWidth − clientWidth`.
