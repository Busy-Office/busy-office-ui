## A. When an item's premise is itself a measurement, the Accept criteria must make re-checking it part of done — **Evidence**

Two rounds in this window (and one immediately before it) were spent refuting a
claim the loop had written into its own plan. In every case the build round
caught it, which is the discipline working. What it cost was a whole round.

The three, with the premise **as the item stated it at triage time** (read from
the commit that introduced each, not from the post-mortem text that replaced
it):

| item | the premise, as written | what the build round measured |
|---|---|---|
| 151.1 | *"`grep` finds no saved-view concept on any of the 39 pattern pages, and it is the single biggest thing in the screenshot the framework has no answer for"* | `/patterns/list-report` ships the whole mechanism. The grep was a context-window regex silently requiring 50 preceding characters. |
| 153.2 | *"21 of 27 suite screens render a date as a plain string like `'01 Oct'`"* | The strings are `<td class="bo-u-tabular">01 Oct</td>` — the prescribed replacement, used 349x. And `bo-date` has been deprecated since 2026-08-19. |
| 151.3 | *"`bo-badge` has five tones and no ordinal channel"* | **True.** Refused on principle, not on premise — the tone word IS the ordinal channel, so a glyph would encode the same fact twice. |

**Neither failing premise recorded the command that produced it.** 151.1 says
"`grep` finds" without the grep; 153.2 states a bare 21-of-27 with no query and
no check of the markup those strings sat in. The next wake could not re-run
either claim — it had to re-derive it from scratch, and in 151.1's case only
found the error by happening to try a plain fixed-string grep.

**The control is in the same window, and it is 149.1.** Its premise was also a
count — four screens hand-rolling a threshold — and the count was right while
the *interpretation* was wrong for three of the four. It cost nothing, because
its Accept criteria said so up front: *"each of the four either uses
`bo-progress` **or** records a one-line reason it should not … refusing per
screen is a valid outcome."* Same shape of error, absorbed by the criterion
instead of by a round.

So the difference is not care, and it is not the measurement. It is one
sentence in the Accept criteria:

- 149.1 — *"each of the four either uses it **or** records why not"* → the
  round's job includes disagreeing with the premise.
- 153.2 — *"the **screens** change, not the component"* → the round's job
  assumes the premise. Disagreeing with it is off-plan, and only the loop's own
  standing discipline (*is this signal present in things I am not counting?*)
  rescued it.

**Counter-evidence.** Three instances, all caught, none shipped, and one of the
three (151.3) shows a stated premise that was simply correct — so this is not
"premises are unreliable". The rate matters too: 23 items across slices
149–158, 3 refusals, 2 of them premise-false. It is a minority failure, and the
loop's build-time discipline caught 2 of 2. The claim here is only that the
catch happened one step later than it needed to.

**The rule this argues for**, and it is deliberately an *amendment to the rule
the last grill already wrote*, not a new section — 158.2 has the loop's own
prose growth open as an item, and a second section restating a neighbouring
idea is exactly what that item is about:

> An Accept criterion names the PROPERTY to verify, never the value it will
> have — **and when the item's premise is itself a measurement from an earlier
> wake, re-checking that premise is part of the criterion, not a courtesy.**
> Write the command next to the claim so the next wake can re-run it in
> seconds, and write the criterion so that finding the premise false is a
> satisfying outcome rather than an off-plan one.

Nothing mechanical is proposed. "Does this criterion admit its premise might be
wrong" is semantic, and roadmap 94.11 already paid for the lesson that a gate
can enforce a shape but not a meaning. This is a writing rule and is recorded
as one.

## B. Two instruments were built to gate the 157.3 shape. One is blind, one is noise. **No gate** — **Evidence**

157.3 found `[dir="rtl"] .bo-data-table td[data-tone="success"]` still carrying
a 3px inset edge after 157.2 removed the cell edge, *"because it was a
standalone rule while danger and warning were grouped into the row selectors
the edit rewrote — so it was not where the edit was looking"*. It concluded no
gate could have caught it. That conclusion was asserted, so this grill tried to
build one. Twice.

**Instrument 1 — the split family.** Predicate: within an attribute-value
family (same selector shape, one `[attr=value]` varying), a property declared
by members living in more than one rule, where at least one of those rules is a
comma group and at least one is standalone. That is literally the configuration
157.3 describes.

Red-proved against the real tree at `3a995d1^` — the commit before 157.2 — and
it **does** fire on the family that was about to break:

```
components/data-table/data-table.css  box-shadow
   .bo-data-table td[data-tone="danger"]  .bo-data-table td[data-tone="warning"]
   .bo-data-table td[data-tone="success"]
```

But look at *when* it fires: on the healthy tree, before the bug existed. It
detects a **pre-condition**, not a defect — "an edit here can leave a sibling
behind", not "a sibling was left behind". Base rate on today's tree: **3 of 15
families**, and all three are legitimate splits by value (an `error` row is
danger-coloured, `dirty` and `warning` are warning-coloured; the three density
tiers hold three different numbers). Three signals, zero defects.

**Instrument 2 — the asymmetry.** Sharper predicate, and the one that actually
describes the bug *as a bug*: a property declared for a **proper subset** of a
family's values. After 157.2, `success` had a `box-shadow` that `danger` and
`warning` did not.

It reports **zero on the tree that carried the live bug** (`3a995d1`). The
reason is structural and worth writing down: 157.2 removed the danger and
warning rules *entirely*, so the family `[dir="rtl"] … td[data-tone=*]` had
exactly one surviving member. A family of one is not a family, and the
asymmetry cannot be seen. Meanwhile on today's healthy tree it reports 3
families and 35 "partial" properties, 27 of them `[data-theme=*]` tokens the
dark theme legitimately overrides.

So the second instrument is **noisy and blind at the same time** — the worst
combination, and it would have looked like a working gate had it not been run
against the actual commit.

**The verdict, now measured rather than asserted: 157.3 was right.** The defect
is *the absence of an absence* — a rule that should have stopped existing.
Nothing in the source structure distinguishes "this rule survived an edit" from
"this rule belongs here"; only the rendered result does. 157.3's answer — a
`check:claims` case reading the **computed** shadow on all three tones and on a
row state, in both directions, red-proved on both halves — is the correct
granularity because it is the granularity the rule is stated at.

**Counter-evidence.** Instrument 1 is not worthless, it is just not a gate: as
a *pre-edit* question ("which siblings will this edit not be looking at?") it
would have flagged the exact family. That is a reading habit, not a build step,
and turning it into a build step would fail 3 of 3 today. Recorded here so the
next person tempted to gate this shape finds the two dead instruments instead
of rebuilding them.

## C. `report-reach`'s zero-reach question is now 7-for-7 adjudicated, and the report carries none of the verdicts for the five it still prints — **Evidence**

Measured this wake, from a clean build:

```
never composed (5): bo-avatar-stack, bo-file-dropzone, bo-file-input, bo-file-list, bo-tree
cannot appear (1): bo-toast-region
deprecated (1): bo-date
```

Seven blocks have ever read zero. **Every one now has a written verdict, and
not one of them is a framework defect:**

| block | verdict | where the verdict lives |
|---|---|---|
| `bo-date` | deprecated — zero reach is the deprecation working | printed by the report ✓ |
| `bo-toast-region` | a runtime container; cannot appear in a static corpus | printed by the report ✓ |
| `bo-tree` | correctly refused at the point of use — every suite hierarchy carries data columns, so `tree-table` rightly wins | a source comment the report never prints |
| `bo-file-dropzone` / `bo-file-input` / `bo-file-list` | instrument gap — no suite screen has an attachment flow | a source comment, and only for the first of the three |
| `bo-avatar-stack` | correctly refused, *strongly* — the suite HAS the approval-chain scenario and renders it as a `bo-timeline` with named steps, states and timestamps, all of which overlapping discs would lose | **nowhere in the script at all** |

The instrument-gap verdict was re-verified independently rather than inherited:
`grep -rilE "attach|upload"` over all 27 `*.screen.mjs` files returns **zero**.

**150.1 refused to gate zero reach on the argument that a gate would be "wrong
roughly a third of the time". The measured figure is seven times out of
seven.** The refusal was right and is now much better evidenced than when it
was made — this is the third time it has been re-refused, and it should be the
last.

**The finding is not the ratio, it is what the report prints.** Of the five
blocks it lists as "never composed", **zero carry their verdict in the output**;
two have it in a header comment a reader of the report will not see, and the
sharpest verdict of the seven is not in the file at all. So the next wake that
reads this output meets five bare block names with no indication that all five
have already been examined and cleared — which is precisely the state that
produced 153.2, where a bare "21 of 27" got read as a defect and queued as a
build item.

Two rounds in this window each moved exactly one block out of the bare list and
into a map with its reason. At that rate the remaining five take five more
rounds. They should take one, and it should not add a third exemption bucket:
these blocks are **not exempt** — they are *adjudicated*, which is a different
and weaker claim that can go stale in a way "is deprecated" cannot.

**Counter-evidence, and it is real.** A 0-for-7 true-positive rate on the
*existing* tree does not measure what the report is actually for, which is a
tripwire for a **new** block shipping with zero reach. That question is still
open and the report is still the only thing watching it. Nothing here argues
for deleting the report — only that a name printed with no verdict reads as an
open question, and five of the seven are closed. The both-ways reconciliation
153.1 added (a listed block that IS composed reports as stale; one that is not
a shipped block reports as renamed) is exactly the mechanism that keeps an
adjudication list from rotting, and it already exists.

Queued as **159.1**.

## D. The mirror's RECOVERY path is what corrupts it — found while re-measuring the refusal rate — **Evidence (one instance, but structural)**

The base rate quoted at the top of this grill was re-measured rather than
inherited from Slice 153's text. The query returned this:

```
since 2026-08-19: landed 346, refused 174, triaged 45, logged 35,
                  shipped 7, released 3,
                  "edited' dirty marker). A context-window regex requiring 50
                   preceding chars produced the false negative"  ← 1
```

That last one is an **outcome column holding a fragment of an item's prose**.
One row in 971, and it is the row recording 151.1's refusal.

**The mechanism, read from the code rather than guessed.** `_common.py` sets
`SEP = " · "` and `parse_log_line` splits the line on it, then assigns fields
**positionally from the left**. 151.1's item text legitimately quotes the
list-report dirty marker — `'Overdue · edited'` — so that line has seven fields
instead of six. `item` gets truncated at the embedded separator, `outcome`
picks up the middle fragment, and `commit_sha` picks up something else again.

**And the corruption is introduced by the recovery path, not the write path.**
`record_iteration.py` builds the log line and the DB row from the *same
in-memory values*, so the live insert was correct. The row only breaks when
`rebuild_from_log.py` — the script whose whole purpose is *"the recovery/verify
path … running it can never drift from the files"* — reads the markdown back.
The storage doctrine says every mirror must be rebuildable from the files; here,
rebuilding is the thing that breaks it.

**Nothing was watching.** `check:loop-vocab` exists and looks like the gate for
this, but it compares the vocabulary *documented in CLAUDE.md and LOOPS.md*
against the Python constant. It never looks at a row. So an outcome value that
is not in the vocabulary at all sits in the mirror unnoticed — which is exactly
the shape CLAUDE.md's own storage doctrine names: *a mirror must reconcile
against its source and fail loudly when it cannot*, and *a derived artefact may
not decide, on its own, what it failed to see*.

**Blast radius, bounded rather than implied.** `dispatch_status.py` reads
`loop-log.md` directly, so the dispatcher counters that decide what this wake
runs are unaffected — this was checked, not assumed. What is affected is
anything that counts by `outcome`: the refusal rate this grill quotes is
really 175/346, not 174/346. Small. The point is not the magnitude, it is that
the mirror disagreed with its source and said nothing.

**Counter-evidence.** One line in 971 carries an embedded separator, measured.
A low base rate is a fair argument against ceremony — but not against this fix,
because the fix is not a new gate: it is (a) parsing the fixed-arity fields
from the RIGHT end, which is exact and removes the failure mode entirely, and
(b) the reconciliation the doctrine already requires — assert every rebuilt
outcome is in the vocabulary and refuse to write if not.

Triaged as **P0**, since it is a shipped script producing a wrong result
silently. Queued as **159.2**.
