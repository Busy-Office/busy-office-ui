## A. When a system TRANSFORMS what you hand it, the authority is what the system serves — not what you handed it — **Evidence**

CLAUDE.md already says *"a bulk edit is verified against the RENDERED
artefact"*. This window shows the rule has a blind spot: it does not say which
artefact is the rendered one when a **third party** does the rendering.

| slice | what was verified | what was authoritative | outcome |
|---|---|---|---|
| **185** | the **tarball**, unpacked twice, reading `bin` from `package/package.json` | the **registry** — `npm view @busy-office/create-ui bin` | wrong conclusion: "npm strips the bin, the scaffolder ships with no executable". npm **normalised** `./index.mjs` → `index.mjs`. The published package was fine all along. |
| **185** | `curl` on the registry read path, twice, plus a published control | the **write** path, which had already answered `E403 cannot publish over 0.1.0` | wrong conclusion: "it was unpublished, 0.1.0 is burned". It was propagation lag on a brand-new scoped package. |
| **187** | the generated `patterns.json` / `patterns-index.json`, byte-compared | same | **correct** — the refactor was proven neutral, and red-proved by removing `.trim()` |

Two failures and one success, and the difference between them is precise: in
187 the generator was **ours**, so its output was the last word. In 185 **npm**
sat between the artefact and the truth, and the tarball was an *input to* the
thing that decides, not the decision.

**The sharpened rule**: verify at the last point the artefact passes through
before a user sees it. If something downstream can rewrite it — a registry, a
CDN, a bundler, a minifier — that thing's output is the artefact, and asking it
is usually one command.

**Counter-evidence, and it lowers the severity a lot.** Both 185 errors were
caught, neither reached a user, and the package was correct throughout — the
cost was one unnecessary version bump (reverted) and a commit message that
overstates a bug. And the control that *did* work in 185 (comparing against a
published package) was good practice that happened to be the wrong control:
`@busy-office/ui` is an *old* package, and the lag is specific to *new* ones.
That is not carelessness, it is a control chosen before the failure mode was
understood.

## B. Re-checking an item's stated premise changed the work in three of four slices — **Evidence**

CLAUDE.md added this rule in an earlier window: *"when the item's PREMISE is
itself a measurement from an earlier wake, re-checking it is part of the
criterion."* This window is the first where following it changed the build
rather than merely confirming a number.

- **173.1** — premise reproduced **exactly** (`c0 2000/0 · c1 160/4 · c2
  2000/0`, table 4200px). Re-checking cost seconds and bought confidence.
- **173.2** — premise **FALSE**, and it would have shipped a regression. The
  Accept criterion said the fact is "carried WITHOUT focus by the row tint plus
  its 3px leading edge, **both already shipping**". Both ship in the framework;
  the demo row had **no `data-row-state`**. Hiding the message on blur would
  have left the error signalled by a red border alone — colour only, no
  non-colour channel — while the commit claimed to be *improving* the pattern.
- **186.2** — premise **decayed while the item was open**. Its Accept asked
  whether the distinction "survives the next rewrite"; it did not, and the item
  was closed by running its own test rather than by argument.

**Counter-evidence**: three instances, all in slices written by recent wakes of
this same run, so this may measure a fashion rather than a durable habit — the
same caveat the 163-165 grill attached to its version of this finding. The test
is whether items written a month from now still get their premises re-run.

**What it does establish**: an Accept criterion that embeds a *forecast*
("both already shipping") is exactly the failure mode CLAUDE.md's "name the
PROPERTY, never the value" section warns about, and 173.2 is the first case
where following the forecast would have shipped a two-channel regression rather
than merely a wrong number.

## C. The loop reported "nothing dispatchable" while a buildable item sat in the backlog, for four consecutive wakes — **Evidence**

186.2 found it; this window closed it and, more usefully, **produced the
counterexample that proves it was not a one-off**. Four consecutive wakes
reported rule 4 as *"all open items owner-blocked"*. 173.2 was not
owner-blocked once the owner answered — it was **browser-blocked**, and the
first local wake to look at it built and landed it the same day.

The failure has a shape worth naming: **a cloud wake reporting "nothing
dispatchable" was telling the truth about itself and a falsehood about the
backlog**, and nothing in the hand-off distinguished the two.

The fix's own first attempt failed the same way the finding describes. The
distinction was written into `RESUME.md` — and `grep -i "browser-blocked"`
returned **nothing** a day later, because that file is rewritten wholesale
every wake. It now lives in `LOOPS.md` rule 4, beside the rule it governs.
**That is 169.3's lesson arriving for the second time**, which is the real
finding: the repo has a durable-vs-ephemeral distinction and keeps writing
durable corrections into the ephemeral file.

**Counter-evidence**: the hand-off is *supposed* to be rewritten each wake, and
it is not obviously wrong for a wake to record a transient observation there.
The defect is not the file, it is putting a **rule** in it. Both instances
(169.3, 186.2) were exactly that.

## D. What went right, recorded so it is not lost

- **187 refused the tempting consolidation.** `wrong-choice-rule.mjs` carries
  the same tag-strip idiom, and folding it into the shared helper would have
  changed what the clause detector matches — it needs the original leading
  whitespace. Recognising that a third occurrence of an idiom is *not the same
  operation* is the distinction the whole sweep exists to make.
- **187 validated its detector before trusting it.** Monotonic decay across
  window sizes (24/14/4/1/0) plus a planted verbatim clone taking WIN=6 from
  1 → 59. A single-hit result on 104 files is exactly the "suspiciously tidy
  number" this repo treats as a defect until shown otherwise.
- **185's release was verified as a CONSUMER**, not from the repo: an empty
  directory, `npm create @busy-office/ui`, and a scaffold that pins the
  published core. That is the check `released` means, and it is why the outcome
  vocabulary distinguishes it from `landed`.
- **186/187 both reported a number moving the WRONG way and explained it**
  rather than hiding it: 187's duplicate count went 4 → 5 *because of* the fix,
  since the two generators' import lines now match. Duplication fell while the
  metric rose.
