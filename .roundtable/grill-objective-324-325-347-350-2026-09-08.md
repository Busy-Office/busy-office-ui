## Finding A — the base rate `350.1` hands forward classifies the sweep's OWN output as lane input

Slice 350's probe windows the log's Standardize commits as `a..b` and asks
whether any commit in the window touched `packages/core/src/css/**` or
`apps/docs/src/**`. `b` is the **sweep's own commit**. A sweep that converts a
dead style therefore lands its conversion inside its own window, and the window
is classified *has lane input* on the strength of the sweep's output rather than
on anything the sweep had to read.

The slice states this in prose about the one window it checked by hand:

> A hand spot-check of the newest closed window (`f9e0f17d..161ede68`) shows
> exactly one of its 16 commits touching a lane input — `161ede68`, **the
> sweep's own conversions**.

Re-run with the window the sweep could actually see when it started (`a..b^`),
against the same log and the same input paths:

```
# probe: same std list, same INPUTS, two predicates
windows=139
  published predicate (a..b, INCLUDES the sweep commit): no-input=15 (10.8%)
  what the sweep could SEE (a..b^, excludes its own commit): no-input=20 (14.4%)
  windows classified has-input ONLY by the sweep's own commit: 5
  those sweeps: 15f9bbc1 91677655 cdd7c07e 0768f09f 161ede68
```

**Discrimination, by hand, on two of the five** — the only lane-input-touching
commit in each window is the sweep's own commit:

```
== window d3bb443f..cdd7c07e
   cdd7c07e Standardize: the docs palette uses the shipped bo-kbd ...  -> 1 lane file
== window f9e0f17d..161ede68
   161ede68 Slice 345 — Standardize sweep, 4 of 4 lanes ...            -> 6 lane files
```

So the rate `350.1` is a decision about is **14.4%, not 10.1%** — understated by
a third, and understated in the direction that weakens the item's own case.
`161ede68` — the window the slice named in prose as the sweep's own output — is
one of the five.

**This is not an arithmetic error and it does not touch the verdict.** 350.1 is
filed, not decided. What it changes is the command a later wake is told to run
to decide it.

### A second, smaller effect on the same number: the wake's own recording moved it

`350.1`'s Accept says *"the figures are snapshots and **this commit does not
move them** (it touches no lane input), but a later one will."* Re-measured at
four revisions, reading `loop-log.md` **at each revision** rather than from the
working tree:

```
81f6281c: windows=138 noin=14 (10.1%) noboth=13 span=1994   <- Step 0 tip
6996a39 : windows=138 noin=14 (10.1%) noboth=13 span=1994   <- the slice's OWN commit
65de70c : windows=139 noin=15 (10.8%) noboth=13 span=2008   <- the SAME WAKE's recording
0ab8a56 : windows=139 noin=15 (10.8%) noboth=13 span=2008   <- HEAD
```

The claim is literally true of the commit and false of the wake. The parenthesis
gives the reason backwards: **a Standardize wake's mandated `record_iteration.py`
step appends a row with the sweep's sha, which adds one window — and that window
is a no-input window exactly when the sweep is the kind `350.1` is about.** So
touching no lane input is what makes the wake move the numerator, not what stops
it. `noboth` stays 13 because that window *did* touch an instrument
(`6cfe380c`, comment-only) — the slice's own classification, arriving as a
control.

The general form, and the reason this is worth writing down rather than
correcting silently: **a figure published from inside a sweep is always one
window short of the sweep publishing it**, because the window only exists once
the wake records. `ENVIRONMENT.md` says where to *read* a figure (from the
commit it describes); nothing said that a wake's own last mandated step can move
a figure the wake published three commits earlier.

Six paths, five named. The omitted one is a `.roundtable/` grill report — the
same *kind* of thing as the roadmap prose the sentence does name, so **the
conclusion is untouched**: nothing that runs cites the script, CI never runs it,
and one `<code>` block can still go stale silently. It is recorded because the
sentence is a closed enumeration prefixed by a claim to have measured it, which
is the shape this repo files as *a real count of a set the sentence does not
name*.

**No item.** The remedy is to write `git grep -l` output rather than a prose
list, which is a habit, not a mechanism, and a gate over "does this prose
enumeration match this command's output" is the semantic shape 94.11 refuses.

**So the corpus is one: `67fc6659`, the one this grill needed.** A gate would be

**What would reopen it, as a property:** re-run the census, separating tokens by

## What this grill's own instruments got wrong

Recorded because CLAUDE.md's base rate says the first output of a new detector
is wrong until checked, and both of these were:

1. **The sha census over-counted 5x** by matching on token shape. Nine
   non-resolving tokens looked like nine dead revision citations; reading the
   context of each showed eight are blob digests or deliberate bogus values, and
   the real corpus is one. That is what turned Observation C from an item into a
   refusal.
2. **The `absent` red-proof came back green on its first run**, because the
   worktree it ran in had no `packages/core/dist` and the gate exits before
   reading a stamp. The injection landed in the file and the gate never got to
   it — the *"a green red-proof is a defect in the injection until proven
   otherwise"* case, caught by reading the output rather than the exit code.

A third was avoided rather than made: `dispatch-region-words` measures **7,548**
today against its newest recorded sample of **7,492**, which reads as a metric
Slice 350 measured and failed to record — and `324.1` names that name as the one
live candidate to reopen rule 5. It is not: `dispatch_status.py` pairs by
**distinct day** and takes the last reading per day, and both the existing
sample and this wake fall on **2026-09-08**, so recording it would replace that
day's value rather than add a third day. Slice 350's non-recording costs rule 5
nothing.
