## C. 205's base rate reproduces; the version it publishes for `@keyframes` is the PREFIXED one — Evidence

205.1's measured base rate is right. An independent regex walk of the built
`packages/core/dist/css/rf-essentials.css` (comment-stripped, a different
instrument from the script's `postcss.walkAtRules`) finds the same **6**
distinct at-rules, and an independent BCD read finds exactly **one above 108**:

```
container 105 · keyframes 43 · layer 99 · media 1 · starting-style 117 · supports 28
```

Five of those six match what the gate's own pass line prints. The sixth does
not: the shipped line reads **`@keyframes 1`**, and 205.1's roadmap text
repeats it.

BCD's entry is an array, and the mechanism is one missing filter:

```
css.at-rules.keyframes.__compat.support.chrome
  = [{"version_added":"43"}, {"prefix":"-webkit-","version_added":"1"}]
```

`earliestChrome()` (`packages/core/scripts/check-rf-floor.mjs:99-107`) filters
`flags` but not `prefix`, so the `-webkit-` entry wins as "earliest". `1` is
the Chrome version for `@-webkit-keyframes`; the profile emits the unprefixed
at-rule, which is **43**.

**The repo has already decided this question, in the sibling script, and the
two have diverged silently.** `derive-floor.mjs:102-115` resolves the same BCD
data through `earliestUsableVersion(support, emitsPrefixed)` and does filter:

```js
const usable = entries.filter((e) => !e.prefix || emitsPrefixed);
```

The two scripts share the `path` column for 6 feature ids, which `LOOPS.md`'s
*"Also settled: the BCD feature paths shared by two floor scripts"* examined and
refused to consolidate on the ground that **divergence there is LOUD** — both
scripts throw with the offending path named. That argument holds for the path
column and does not extend to the resolution helper sitting beside it, where
divergence is silent and has now happened.

**Direction of the error, which is the part that decides severity.** Taking the
prefixed version *understates* the floor, so this reporter can only ever produce
a false "below 108" — the false-safe direction, in a script whose entire job is
that floor.

**Blast radius today: zero verdict changes, measured rather than assumed.**
`43` and `1` are both below 108, so `@keyframes` is classified identically
either way, and the "1 above 108" total is unaffected. None of the four
`FEATURES` probes can hit the bug at all — every one has a single unprefixed
support object:

```
:user-invalid {"version_added":"119"} · color-mix() {"version_added":"111"}
subgrid {"version_added":"117"} · :has() {"version_added":"105"}
```

**One thing that looks like a second bug and is not.** `earliestChrome`
computes `live` (entries without `version_removed`) and then uses `entries`:
`const pool = live.length ? entries : []`. That is deliberate, and
`derive-floor.mjs`'s header explains why — Safari lists `accent-color` as
partial from 15.4 with `version_removed: 26.2` and full from 26.2, so
discarding removed entries put the floor two years into the future. The
sibling has the identical shape. Withdrawn before it was filed.

Filed as 209.2 rather than fixed here: a grill that rewrites the gate it is
grilling is marking its own homework, and 205 itself was *filed rather than
fixed* from inside the 200.4 dispatch for the same reason.
