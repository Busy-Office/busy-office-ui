Measured in the DOM over all **127** built pages: **33** text nodes containing

The chain, each link measured: `kanban.astro:243` writes correct markup
(`Dashboard &amp;amp; widgets` in source) → `pattern-extract.mjs`'s `BADGE_RE`
captures `([^<]+)`, nine characters of SOURCE, into `patterns-index.json` and
`patterns.json` → `patterns/index.astro:38` renders `{c.label}` as a text node,
so Astro escapes the `&` again. The same omission had put **52** entity
references into `patterns.json`; `dist/llms.txt` carried **0**.

### Why 263.1's criterion could not see it — the transferable part

263.1's Accept (a) read *"exactly one entity decoder exists in the directory,
counted STRUCTURALLY over comment-stripped source"*. That is **true**, and it
was executed honestly. It counts the **answers**, not the **questions**: a file
that needed to decode and did not is invisible to a census of decoders, the way
a survey of alarms cannot find the room without one.

The property that finds it is downstream and is about the artefact, not the
source: **does any text this directory PUBLISHES still carry the spelling of
its source?** That is checkable in the DOM, which is where it was found.

Worth stating precisely, because the neighbouring claim is wrong: this is *not*
"263.1 should have looked harder". Its lane-5 name-collision scan could not
have found it either (263.1 says so about its own finding, for a different
reason), and neither could a wider census. The criterion was the right shape
for the duplication it was closing and the wrong shape for the gap beside it.

### The fix, and the rename that is the point of the rename

`stripTags` → `textOf` in `pattern-extract.mjs`: strip tags, `decodeEntities`,
collapse, trim — reading the module 263.1 created, one directory over. Order is
load-bearing and **red-proved rather than argued**: decode-first turns
`&lt;b&gt;` into real tags the strip then deletes, and the new self-test case
fails with `renders none inline` when the two are swapped and with
`renders &lt;b&gt;none&lt;/b&gt; inline` when the decode is removed — the
mutated line grepped back out of the file before each run.

263.1 logged core's byte-identical `stripTags` as a deliberate
non-consolidation and said to reopen *"if either copy grows a case the other
does not have"*. This is that case, so the shared name goes: two functions that
no longer agree must not keep a name that says they do. **Core's copy is
correct as it stands and was checked, not assumed** — `readme-facts.json`
carries **0** entity references, so it has nothing to decode.

### What the fix does NOT cover, said plainly

**Seven** entity references remain in `patterns.json` / `patterns-index.json` —
`&mdash;`, `&rsquo;`, `&times;`, `&minus;` — names `html-entities.mjs`
deliberately leaves verbatim rather than guessing at. **None reaches a reader
today**, and the reason is a length, not an assertion: the one in an opener sits
at index **317** of an **855**-character string that `gen-llms.mjs` truncates at
220 and `/patterns/` truncates for its tile. That is latent, not live.

**Widening `NAMED` was measured rather than waved off, and refused.** The
tempting argument against widening — "it would rewrite the entity references
shown in code samples on `/components/amount/` and `/components/quantity/`" — is
**false**, and measuring it is what showed that: those samples sit in the built
page as `&#x26;mdash;`, and a one-pass decoder yields `&mdash;` under both the
current and a widened map, because a character it emits is never re-scanned.
What a widened map *would* change is an unescaped `&times;` used as live content
(`<span class="bo-amount__unit">&times; EA</span>` decodes to `× EA`). So the
refusal stands on a real risk, not the one first reached for — and on
proportion: widening a module 263.1 has just settled, to fix seven strings that
nothing renders, is not worth a rebuild's worth of blast radius. The new gate
watches the surface, which is where they would appear.
