## A. 173.2 — the fix is right and its two constants are not

### What reproduces exactly

Re-measured on the built page, headless Chrome at 1440×1000:

```
FACTS      describedby=line-1-qty-err   msgDisplayUnfocused=none   rowState=error
AX unfocused  description: "Exceeds on-hand (200)"   ← while the message is display:none
AX focused    description: "Exceeds on-hand (200)"
HEIGHTS    row 52.5px focused AND unfocused; sibling inputs at 426 both times
           msg box 46px, container padding-block-end 56px, 19px to spare
NARROW390  msg 46px, 15px to spare
```

So all four load-bearing claims hold, including the one most likely to have been
wishful: **the accessible description is computed while the message is
`display: none`**, because it is *directly referenced* by `aria-describedby`
(accname's hidden-node exception). The docs sentence *"`aria-describedby`
carries the reason to a screen reader continuously, focused or not"* is true, and
now measured rather than reasoned.

**Blast radius, asked of the DOM rather than of grep.** The new rule is a shared
selector (`.bo-data-table .bo-form-field …`), and this repo's rule is that the
reported page passing is not the check. Walking **all 138 built pages** and
querying `.bo-data-table .bo-form-field__message`:

```
scanned 138 pages -> 1 hit: /patterns/editable-grid/ ("Exceeds on-hand (200)", display:none)
control: /components/form/ has 1 .bo-form-field__message   (so the query is not dead)
```

**1 of 138.** Zero collateral — and the control is there because a plain zero is a
defect until proven otherwise. A page-level `grep` said **9 of 138** pages
contain both class names; the DOM says one actually nests them. The grep is the
weaker instrument and is recorded so nobody re-derives it.

### The defect: a constant reserve for a variable-height box

`data-table.css` reserves `padding-block-end: 3.5rem` while a message is shown,
and caps the message at `max-inline-size: 18ch`. Both were chosen against the one
21-character string the one demo carries. Every mutation below asserted it had
landed before its measurement was believed (`textChanged: true`, the density
attribute and `--bo-density-row-height` read back):

| trial | msg box | reserve | clipped past the container |
|---|---|---|---|
| as shipped, 1440 | 46px | 56px | **−19** (fits) |
| as shipped, 390 | 46px | 56px | **−15** (fits) |
| message 2× longer (40 chars) | 64px | 56px | **−1** (fits, barely) |
| message 4× longer (101 chars) | 118px | 56px | **+53 — clipped** |
| `data-density="spacious"` | 46px | 56px | −23 (fits) |
| spacious + 101-char message | 118px | 56px | **+49 — clipped** |
| `data-density="compact"` | 46px | 56px | −15 (fits) |

**Severity, corrected by measurement rather than by reasoning — this was drafted
as a P0 and is not one.** The container is `overflow: auto`, so the clipped
region is *scrollable*, not lost:

```
scrollHeight 203  clientH 149  scrollable 54  reachedByScrolling 54  needed 53
```

The reader must scroll the table container to finish reading a validation
message; nothing is unreachable, and `aria-describedby` carries the full string
to assistive tech regardless. So: a real quality defect in a just-shipped
contract, not a P0.

**It is nonetheless a regression, and the control says so.** Neutralising exactly
the three rules 173.2 added (asserting `position` went back to `static` before
believing it) and re-measuring the same 101-character message:

```
AFTER  173.2 (as shipped)   row  52.5   msg 118px (6 lines at 18ch)   clip +53
BEFORE 173.2 (neutralised)  row  92.5   msg  36px (1 line, cell width) clip  −9
```

Before the fix the message was fully readable and the row shifted. After it, the
row is stable and the message needs a scroll. **The 18ch cap is the bigger half
of the cause** — it converts a one-line message into a six-line box, which is
what overruns a 3.5rem reserve. That is not visible on any shipped page, because
the corpus has exactly one such message and it is 21 characters long.

Filed as **190.1**.

### The specificity comment states two wrong numbers

`data-table.css:442` says the new rule *"Beats the `:is(:has([aria-invalid]), …)
.bo-form-field__message` rule in form-field.css on specificity (0,3,0 vs
0,2,0)"*.

Measured, not computed — each selector was raced against references of known
specificity placed **later** in the sheet, so a tie resolves to the reference and
"real wins" means strictly greater:

```
.bo-data-table .bo-form-field:not(:focus-within) .bo-form-field__message
  beats (0,3,1), loses to (0,4,0)   ->  (0,4,0)      comment says (0,3,0)

:is(.bo-form-field:has([aria-invalid="true"]), .bo-form-field:has(…:user-invalid)) .bo-form-field__message
  beats (0,3,0), loses to (0,3,1)   ->  (0,3,1)      comment says (0,2,0)
```

**(0,2,0) is a real specificity in that file — it belongs to the other rule.**
`[aria-invalid="true"] ~ .bo-form-field__message`, the no-`:has()` fallback, is
exactly (0,2,0). The comment names one rule and quotes its neighbour's number.

The **conclusion is correct and independently confirmed**: (0,4,0) beats both, so
the reveal does not depend on import order, and the live reading is
`display: none` as intended. This is an accuracy defect in a load-bearing
comment, not a rendering bug — and comments in this repo's CSS are load-bearing
by construction — `check:slice-refs` resolves its citations out of them, and
reports the count on every run rather than pinning one here.

Filed as **190.3**.

## D. The same shape in the loop's own durable files — both corrected in this wake

### D1. `ENVIRONMENT.md` trap 1 blamed a missing branch for a wrong command

The file says a container with **no local `main`** "shows up one command
earlier: `git rev-parse --short main HEAD` exits **128** with `fatal: Needed a
single revision`", and the previous hand-off recorded that as trap 1 "exercised
for real".

That command exits 128 **whether or not `main` exists**, because `--short`
accepts a single revision:

```
git --version                     # 2.43.0
git rev-parse --verify main       # main exists
git rev-parse --short main HEAD   # fatal: Needed a single revision   rc=128
git rev-parse --short=8 main HEAD # fatal: Needed a single revision   rc=128
git rev-parse main HEAD           # both shas    rc=0
```

So the documented diagnostic reports "your `main` is missing" on every container,
including this one, where `main` was present the whole time. A wake following it
would fix a branch that is not broken. `git rev-parse main HEAD` — no `--short` —
is the command that answers the question. Corrected in `ENVIRONMENT.md`.

### D2. "A cloud wake cannot take 173.2" — it could have

**The concurrent grill (Slice 189, finding C) reached this first and from a
different direction** — the dispatch record, four wakes reporting "all open items
owner-blocked" while `173.2` was merely browser-blocked — and fixed it by adding
the three-way owner-/browser-/agent-blocked split to `LOOPS.md` rule 4. That is
the finding, and it is theirs. What follows is one clause in it, sharpened by
having actually run the measurement.

`186.2`, the last hand-off, and now that new bullet classify `173.2` as
**browser-blocked**, the bullet reading *"needs Podman, a real browser,
screenshots at 1440 and 390"*.

Every measurement in §A of this report is exactly that, taken in this cloud wake:
row height focused vs unfocused, the sibling shift, a red-proof by neutralising
the shipped rules and re-measuring. A cloud wake has **no Podman and no
screenshots**; it has a real Chrome, driven by `browser-harness.mjs` +
`serve-dist.mjs`, which is the same browser `check:claims`, `check:layout` and
`test:axe` already use here every wake.

The conflation is in the wording, not the judgement: `ENVIRONMENT.md` correctly
says the *live-verify step* — screenshots at two widths in two themes — cannot
run, and that got read as "no browser". The distinction now stated there is:

- **cannot run**: anything whose evidence is a *rendered image* a human compares;
- **can run**: any measurement expressible as a DOM, computed-style,
  layout-geometry or accessibility-tree assertion.

`LOOPS.md` rule 4's new bullet is amended to match — "needs Podman and
**screenshots**", not "needs a real browser" — pointing at those two lists, and
asking a declining wake to name which one the item needs. **A three-way split
that mis-sorts is the same failure the undifferentiated word had**, one level
finer.

n = 1 dispatch declined on this reading, so this is a wording correction with a
small measured cost, not a claim that the loop has been broadly wrong.
