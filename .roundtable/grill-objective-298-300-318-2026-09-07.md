## Finding A — a removal verified against raw text, inside a slice about determinism

Slice 318 published **"the 99 other fixed waits"** three times: the roadmap
item, the commit message, and the hand-off. The figure is **98**.

The mechanism is the one CLAUDE.md already names in *"Verifying a removal:
assert on structure, never on raw text"* — **the comment written by that same
edit legitimately names the thing removed.** The fix deleted one real
`setTimeout` wait and added a comment reading *"This read `setTimeout(400)`…"*,
so a raw grep reads the same number on both sides of the change:

```
raw `setTimeout` occurrences      parent 99   HEAD 99      ← identical across inputs that must differ
comment-stripped                  parent 99   HEAD 98
the wait idiom, `new Promise((r) => setTimeout`
                                  parent 99   HEAD 98      ← needs no stripping at all
```

Two independent instruments agree on 98 and neither depends on the other. The
tell was available without either: **an identical value across two inputs that
must differ is a defect until proven otherwise**, and this repo's own base-rate
section says so.

The conclusion the number supports — *leave the other waits, a sweep of them is
a Standardize lane* — is unchanged at 98 or 99. What is damaged is the audit
trail, which is the half a later wake re-runs. **Amended in place at the end of
Slice 318, with both commands.**

This is the fourth recorded instance of 192.1's shape: **the expensive
verification went to the claim the work was about — the red-proof of the race,
which is exemplary — and the sentence beside it went out on credibility having
earned none.**

## Finding B — the surviving two thirds of a corrected claim, one of them false

Slice 317's finding was that `/patterns/kanban` claimed something its demo
cannot do. The audited sentence read:

> The menu already gives every card **a keyboard path**, **a
> screen-reader-announced result**, and **a touch target that works with
> gloves**.

Three claims. The slice measured the middle one, found it false, removed it, and
**re-published the other two without measuring either**. Measured here:

```
KEYBOARD PATH — real key events (page.keyboard, never el.click())
  trigger focused                          true
  popover open BEFORE the key              false        ← the control half
  Enter                                    open: true   ← holds
  Tab                                      lands on "Move to In progress" (inside #kb-menu-1)
  control run, no keys pressed             open: false; items measure 0x0

GLOVE TARGET — geometry on the built page
  menu item                                182 x 37
  per-card trigger                         60 x 24      at 1440px AND at 390px
  all five per-card triggers               .bo-btn--sm[popovertarget]
```

**24px is not a glove target on this framework's own scale**, and the scale was
measured on the built site rather than quoted from prose:

```
bo-btn @ compact / comfortable / spacious    28 / 36 / 44      (reproduces /concepts/density)
bo-btn--sm, default density                  24
bo-btn--sm @ spacious                        24               ← does not move at all
control: an unstyled <button>                23               (so the tiers are the framework's, not the UA's)
source: .bo-btn--sm { --bo-btn-height: 1.5rem }   button.css:121
```

So the target cannot reach the glove tier by any density setting a consumer
applies — the `--sm` height is fixed. `/concepts/density` states outright that
24px is the **WCAG 2.5.8 minimum met through the spacing exception**, not a size
floor, and `/components/button` calls spacious *"the glove tier, as everywhere"*.
`/components/data-table` makes the same distinction from the other side: *"the
RF track's bar is a gloved thumb, and 18px is not that."*

**Nothing gates either claim.** `check:target-size` sweeps **7** pages and
kanban is not one — and adding it would not have caught this, because the menu
items measure `0x0` while the popover is closed, which is the state a sweep
finds them in. The single existing `check:claims` kanban case drives
`page.click` and asserts popover open/close; it says nothing about a keyboard
path.

## The pattern across both findings

Neither defect is in the thing its slice set out to prove. Slice 318's red-proof
of the race is a model of the discipline — an injection with a control, checked
for discrimination, reproducing CI's exact reading — and the sentence beside it
was counted with a grep that could not tell before from after. Slice 317
measured a spike across two boards with a control run, refused a component on
the reading, and re-published two unmeasured claims in the sentence it was
correcting.

**Both are the same instruction:** the verification budget goes where the
argument is, and everything travelling beside it goes out unexamined. The
repo's own answer is already written (*list the other claims a change is
carrying and name the instrument for each*); what this grill adds is that **a
sentence you are editing is not thereby a sentence you have checked.** Slice 317
had the audited claim open in front of it, corrected one third of it, and left
the other two thirds standing — which is a narrower and more avoidable failure
than a number quoted from memory somewhere else in the file.
