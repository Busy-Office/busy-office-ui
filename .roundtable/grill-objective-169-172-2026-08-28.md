## A. Every red-proof that failed in this window failed in the INJECTION, never in the detector — **Evidence** (5 instances, 2 slices)

CLAUDE.md already carries this rule, in bold, with five worked examples:
*"Red-proving a gate: verify the INJECTION, not just the red result."* It was
violated five times in two slices, by an agent that had read it.

| slice | the red-proof | why it lied |
|---|---|---|
| 169.4 | put the charter check back into `check:repo`; gate must go red | stayed **green**. The glob reader reused `readsFile`'s `NAME = path` heuristic — a directory prefix starts with `.`, a regex wildcard |
| 169.4 | same, second attempt | stayed **green**. Workspace script maps were flattened, so the root's `build` overrode the docs `build` and the chain stopped before `check:repo` |
| 169.4 | same, third attempt | stayed **green**. A bare `npm run X` inside a workspace script means X in THAT workspace; it was resolved against the root |
| 172.1 | regress the copyable CSS to `overflow: hidden` | stayed **green**. **Two copies of the rule exist** and the injection hit the live demo, not the copyable block |
| 172.1 | the static claim itself | tripped on **its own explanation** — the sample's comment says *"With overflow:hidden the results listbox does not render"*, so a raw-text assertion matched the prose |

**The pattern is sharper than "be careful".** In every case the detector was
fine and the *injection* was wrong, so the gate reported a true "nothing is
broken" about a change that had not been made. A green red-proof is therefore
**not weak evidence — it is no evidence at all**, and it is indistinguishable
from success unless someone treats the silence as suspicious.

So the operational rule is not "verify the injection" (already written, already
ignored) but: **a red-proof that comes back green is a defect in the injection
until proven otherwise.** Same grammar as this repo's other base-rate rules —
*a 0%, a 100%, or an identical value across many inputs is a defect until
proven otherwise* — and it is the form that actually gets acted on, because it
names the observation rather than the intention.

**Counter-evidence, and it is decisive about severity.** All five were caught,
none shipped, and each was caught by the same habit: doing the red-proof at all
and refusing to accept silence. A process that produces five caught injection
errors is not obviously worse than one that skips the step and produces none
visible. And the previous grill's parallel finding — three name-derivation
errors against an existing rule — makes this the second window where **a
written rule did not reduce its own violation rate**, which argues the rules
are working as *diagnosis* rather than as *prevention*.

## B. A gate is exempted from proving it can fail by its OWN declaration, and nothing checks the declaration — **Evidence**

`check:selftests` requires every `@heuristic` gate to ship `--self-test` and
exempts every `@exact` one. The tag is written by the gate's author, in a
comment, and is never verified.

Two instances, one week apart in the same window:

- **`check-resume-charter.mjs`** shipped tagged `@exact` on the grounds that
  "both halves are string membership… There is no recognition step to fool",
  while its second assertion ran a heading-vs-fence **state machine**. Found by
  the 168-170 grill, *by running the parser rather than reading it*, and shown
  to **fail open** on the real file.
- **`check-ci-ignores.mjs`** — found here, and it is the gate this window's own
  169.4 modified. It was tagged `@exact` because it "opens each script and
  looks for a real read", but that IS recognition: `readsFile` decides from
  call shapes whether a mention is a read, and the file's own header records
  that a naive version "would fail on every one of those four comments". 169.4
  then made it *more* recognition-heavy by adding directory-prefix matching,
  whose first version flagged a path inside a `<code>` tag in generated HTML.

**Base rate measured before proposing anything**: of **38** `@exact` gates, a
crude scan for recognition-shaped code flags **2**. So this is not endemic —
which is exactly why a gate for it is refused below.

**Fixed here, not queued**, because this grill's own slice caused half of it:
`check-ci-ignores` is re-tagged `@heuristic` and carries a 7-case self-test
whose NOT-flagged cases are the false positives that actually occurred — the
`<code>` tag among them. `check:selftests` now counts 14 heuristic gates.

**Refused: a gate that detects mis-tagging.** It would be a heuristic about
heuristics, at a 2-in-38 base rate, and its own predicate ("does this file
contain recognition?") is exactly the kind of judgement this file records
detectors failing at. The honest control is that a grill runs the parser rather
than reading the tag — which is what found both instances.

**And the self-test needed two attempts too**, which is finding A again, one
level up: the first red-proof of it removed comment-stripping, which does not
affect the `<code>` case at all, because that string is a template literal and
the protection is the call-shape narrowing. Widening `opensPath` to a bare
mention is what made it fail correctly.
