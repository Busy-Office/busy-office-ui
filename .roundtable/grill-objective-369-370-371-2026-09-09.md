## 1. THE FINDING — rule 5 discards a sample on a stated reason that is false at 72 of 73

`per_day_last` keeps only the last sample of each calendar day, and records why:

```python
def per_day_last(samples, name):
    """The last value recorded for `name` on each day, oldest day first.

    The last and not the first: a wake that samples twice in one day is
    correcting itself, and rule 5 compares what each run concluded.
    """
```

That is a claim about the data, so it was checked against the data. **A sample
separated from the next by a commit cannot be a correction of it — the thing
measured changed in between.** Counting distinct commit shas strictly between
each adjacent intra-day pair, over all 143 samples in `loop-metrics.jsonl`:

```
adjacent pairs with NO commit between (a wake correcting itself):  1
adjacent pairs separated by >=1 commit (distinct trees):          72
```

The single pair matching the docstring is `behaviors_frozen`, **19.0 → 18.0 at
the same minute**, `2026-08-16 11:25`. Every other intra-day pair spans between
2 and 50 commits.

**The case the rule was built around is the clearest counterexample.** Three
places assert `ci-wall-time`'s 26 samples are one wake's burst — `LOOPS.md:609`
(*"A name sampled repeatedly inside one wake is not two runs — `ci-wall-time`'s
26 samples all fall in 17 hours of 2026-08-18"*) and `dispatch_status.py:933-934`,
which says it outright: *"a burst inside one wake is NOT two runs.
`ci-wall-time`'s 26 samples are exactly this shape."* Measured over that window:

```
ci-wall-time window 2026-08-18 02:48 .. 2026-08-18 19:54
  loop-log rows in window : 36
  distinct commit shas    : 35
  distinct loops named    : ['Continue','Explore','Objective','Roadmap','Standardize']
```

Thirty-five commits and five different loops. The 17 hours are real; "one wake"
is not.

### What it costs, measured rather than argued

Rule 5's trigger is *"regressed on TWO CONSECUTIVE runs"*. The implementation
maps *run* to *calendar day*, and 72 of 73 discarded samples were separate runs.
For the 8 day-paired names that are rule 5's actual input set:

| name | published (per-day) | last two ACTUAL samples | |
|---|---|---|---|
| `dispatch-region-words` | 7492 → 7484 **−8** | 7552 → 7484 **−68** | **differs** |
| `components` | 25 → 30 **+5** | 29 → 30 **+1** | differs |
| `claims` | 169 → 176 **+7** | 170 → 176 **+6** | differs |
| `bundle-gz-kb` | 11.7 → 15.1 **+3.4** | 15.1 → 15.1 **+0.0** | differs |
| `behaviors_frozen` | 16 → 18 **+2** | 19 → 18 **−1** | differs, and inverts sign |
| `ci-gates`, `gates`, `axe-violations` | | | agree |

**5 of 8 names publish a movement that never occurred between any two samples.**
And on the rule's own predicate — two consecutive moves in one direction — the
two readings **disagree on 3 of 8** (`behaviors_frozen`, `ci-gates`,
`dispatch-region-words`): true at sample level, invisible at day level.

### Why this grill is where it surfaced

`dispatch-region-words` is the extreme case, and **its two same-date samples
were written by two different wakes nine hours apart.** Attributed by
`git blame --line-porcelain` on `loop-metrics.jsonl` — 164.2's method, and the
one `353.2` exists because a sample carries no commit of its own:

```
line 141  7552  2026-09-09 00:55   4cfb8b2c  "record Slice 363 …"  (00:58 +0000)
line 143  7484  2026-09-09 09:44   61e9d92f  "record Slice 371 …"  (09:49 +0000)
```

Slice 370's wake sits between them (08:54), read the region at **7,552** in its
lane-4 write-up, and **recorded no sample at all**. So the discarded reading is
not a correction Slice 371 superseded — it is another wake's correct reading of
an earlier tree, and rule 5 never sees it.

Slice 371's hand-off states the movement as *"the region genuinely moved
(7,552 → 7,484)"* — a −68 — while `dispatch_status.py`, run in that same wake,
printed `2026-09-08 7492 -> 2026-09-09 7484  -8`. **Two numbers for one
movement, 8.5x apart, in one wake's record, unreconciled.**

**Evidence, not Hypothesis** — two independent sources: the commit boundaries in
`loop-log.md` against the sample stamps in `loop-metrics.jsonl`, and the live
output of `dispatch_status.py` itself, which printed the −8 at this wake's Step
0b before any of this was measured.

### What these numbers do NOT cover

- **"Two consecutive moves in one direction" is the SHAPE of rule 5's predicate,
  not its verdict.** No direction is recorded with a sample (324.1), so a rise is
  a regression for `bundle-gz-kb` and the goal for `claims`. The 3-of-8
  disagreement is about what the rule can SEE, not about what it should fire on.
- **A commit between two samples proves they read different trees; it does not
  by itself prove different wakes.** One wake can commit twice. The one-wake
  reading is refuted for `ci-wall-time` by the five distinct loop names, not by
  the commit count alone.
- **This does not establish that the day unit is WRONG.** 324.2 already measured
  `bundle-gz-kb` under four pairings and argued its sample-to-sample moves are
  noise; for a shared-runner timing that is plausible. What is measured here is
  that the recorded JUSTIFICATION for the unit is false, and that the case cited
  for it is mislabelled. Those are separable, and only the first is established.
- **353.2 is adjacent and is NOT this.** It asks that a `dispatch-region-words`
  sample be traceable to the commit it describes. This is about which samples
  the pairing keeps. Deliberately not folded together, and no duplicate filed.

## 4. Three instrument defects in THIS grill's own work

Recorded because the base rate says to expect them, and all three are textbook
shapes.

0. **Authorship inferred from timestamp proximity instead of measured.** The
   first draft of §1 said both `dispatch-region-words` samples *"were written by
   slices in this arming set"* — because 7,552 sits between Slices 370 and 371
   in time. `git blame` says the wake that wrote it recorded **Slice 363**, and
   Slice 370 recorded no sample at all. Caught before publishing, by running the
   very blame the paragraph was about to cite `353.2` for. **The finding is
   unchanged** — nothing in it rests on which slice authored a sample; only the
   narrative sentence was wrong, and it is now sharper for being measured.

1. **The commit-boundary probe was dead on its first run.** It called
   `r.get("sha")` on rows from `dispatch_status.rows()`, which returns only
   `at`, `loop` and `item` — so the set was always empty and it reported
   **0 commits between for 17 of 17 buckets**. Caught by the identical-value
   tell, not by review. Fixed by extracting the sha from the row text, and only
   believed after a **positive control** (9 distinct shas on 2026-09-09) and a
   **negative control** — the detector must be able to return 0, and it does,
   exactly once, on the same-minute `behaviors_frozen` pair. A 17-of-17 verdict
   with no case that reads the other way would have certified nothing.
2. **A paraphrase-grep reported a false absence.** Checking 371's "one copy in
   the archive" claim, `grep -cF` for `"12 of 17"`, `"crossings 51"` and
   `"18 rows"` — the wordings in `ROADMAP.md`'s summary of the move — returned
   **0** in both files. The text is present; the archive writes it as *"18
   Polish rows naming 17 slices, 12 of which no Continue/Standardize row names
   at all"* and *"moves crossings only 51 → 52"*. Not reported as an absence;
   caught by opening the paragraph. This is CLAUDE.md's *grepping the source
   spelling* trap with a paraphrase in place of a minifier.

## 5. Refused, with the measurement

**A gate asserting "a metric sample must not be discarded when a commit falls
between it and the next".** Refused on base rate, which is the rule for a gate
before it ships: the predicate is true of **72 of 73** intra-day pairs today, so
the gate would be red on a correct tree from its first run. This is 94.11's
finding in the other direction — there a predicate true of 100% distinguished
nothing; here one false of 99% would fail everything. The property belongs in
the pairing's own reasoning, not in a build gate.
