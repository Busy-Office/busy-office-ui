## B. THE FINDING — the width cap bounds the message's WIDTH, not its RIGHT EDGE, so the message does introduce horizontal overflow

Same probe, reading `container.scrollWidth` blurred and focused. The container
is the clip box (`overflow: auto`), so its `scrollWidth` growing is exactly
"horizontal overflow was introduced".

```
   w  density      msg      clientW  swBlur  swFocus  grew  msgRight − containerRight
1440  compact      247ch      896      896      896     0        −261
1440  comfortable  247ch      896      896      896     0        −257
1440  spacious     247ch      896      896      896     0        −251
 390  compact      247ch      310      310      393   +83         +67
 390  comfortable  247ch      310      310      394   +84         +68
 390  spacious     247ch      310      370      416   +46         +90
 390  compact       21ch      310      310      310     0         −86   (control)
```

At 390 compact and comfortable the container had **no horizontal scroll at all**
before the message was shown (`swBlur === clientWidth === 310`) and **83-84px**
of it afterwards. The message's own right edge sits 67-90px past the container's.

**Why.** `max-inline-size: min(48ch, 100cqi)` caps the message's *width* at the
container's inline size, but the message is `position: absolute;
inset-inline-start: 0` inside the cell's `.bo-form-field`. Its right edge is
therefore *cell offset + width*, and at 390px `100cqi` is the whole container,
so a message that wants the full cap overflows by exactly the cell's offset.
A cap on width cannot bound an edge that starts at a non-zero offset.

**Red-proved in both directions, each injection confirmed to have landed by
reading the computed `max-inline-size` into a plain string first** (the live
`getComputedStyle` trap 190.2 recorded):

```
cap                     computed          swGrew   msgRight−cRight   msgBottom−cBottom
(as shipped)            310px               +83          +67              −29
6ch                     45.8086px             0         −197             +601
max-content             max-content       +1264        +1248             −119
min(48ch, 100cqi)       310px               +83          +67              −29   (identity)
```

The detector reports **zero** on 9 of 12 rows in finding A and on the `6ch`
injection, so it is not a detector that cannot fail; `max-content` moves it by
1264px, so it responds monotonically to the variable under test; and re-injecting
the shipped value reproduces the shipped number exactly, with
`injectionLanded: false` correctly reported for that identity case.

**Severity: not a P0, on the same grounds 190.1 used for its own finding, and
checked rather than assumed.** The overflow is inside an `overflow: auto`
container, so it is reachable by scrolling, and `aria-describedby` carries the
full string to assistive tech regardless. **No shipped page is affected**: the
137-page DOM walk (below) finds one page nesting a message in a data table, its
message is 21 characters, and that message's own row reads `swGrew 0`.

**This probe was wrong twice before it was right, which is the base rate landing
on the wake that was checking someone else's numbers.**

1. Three of five reference selectors matched nothing (`span.bo-form-field…`,

2. The subject selector was **paraphrased**, not copied: `:has(:user-invalid)`
   instead of the shipped `:has(input:user-invalid, …)`. Those differ by exactly
   the (0,0,1) that decides this question, so the run reported **(0,3,0)** and
   would have filed 190.3's corrected comment as wrong. **Copy a selector from
